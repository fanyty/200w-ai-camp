# 设计对齐与蓝图确认

仅在 Feature 的设计对齐阶段读取。目标是和用户聊清产品骨架、本期 scope 的设计及未来不可逆约束，不按提问轮数收尾或凑轮数。

本期无新增或受影响 UI 时，只核对真实业务流程、角色权限、数据集成、技术与安全等必要非视觉决策；跳过页面、交互和风格维度。仍使用下方同一份蓝图，省略不适用的 UI 章节和条目，不新增无 UI 模式、表单或占位文件；本期有 UI 影响的部分仍须完整设计。

开问前核对已确认的业务目标；共享对话或上游已有明确确认时直接继承，不再单独请用户确认一次。对尚未明确且会改变结果的关键判断给出依据与推荐，由用户拍板。未确认的关键事项不以 TBD 或假设代替。

## I.1 提问与模式

继承上游模式：只接受 `standard / tech-constrained`。`standard` 按当前依赖前沿推进；`tech-constrained` 先确认影响方案的架构/NFR 可行性，若无法满足则输出影响证据并退回 prd-master 修订受影响需求，不得静默放宽需求。读到其他值时暂停依赖模式的决策并退回 prd-master 修正，不自行解释或新增流程模式；无依赖的设备、风格等信息仍可收集。

1. 每个问题优先用当前环境的结构化提问能力，是**选择题**；工具不可用时才按「运行环境适配」退化为纯文本。
2. 每题给 **2-3 个建议选项**并允许自定义，**第一个是 AI 推荐项**，label 末尾标"（推荐）"，description 写清**为什么推荐**。
3. **⭐ 问题必须有洞见、针对这个 PRD 的行业与处境**——推荐理由必须从 PRD 真实信号推出来，不许泛泛而谈。
   - 反例（不许）：「你想要浅色还是深色？」
   - 正例（必须这样）：「我从 PRD 读到这是**内容团队天天坐着用的 B 端生产工具**、要长时间盯着大量视频素材列表，所以我判断用**浅色通透**比深色护眼更合适（深色更适合值守大屏）——对吗？」
4. **按依赖前沿批量提问**：把当前已有足够依据、答案互不依赖的问题同轮提出；依赖前一答案的问题等回答后再问。不固定每轮 1-2 题，也不一次铺开所有维度。遵守当前提问工具的容量，按用户容易一起回答的业务主题分组；等待答复时继续不依赖该答案的工作。
5. **先挑战、再提问**：每题前先说一句"我从 PRD 读到 X，所以判断 Y"，让用户在你的判断上确认或推翻。这就是苏格拉底——不替用户瞎选，是把判断摊开让用户拍板。
6. **PRD 或共享对话中用户已明确确认且无冲突的事项直接继承**，在总蓝图中一并呈现，不逐项重问。Design 主入口检查通过前，只可只读收集已提供的端形态、设备约束、品牌素材和风格偏好，不提前形成正式蓝图或设计产物。若原文仍有多种业务解释，或设计建议改变了已定范围，摊开依据继续问；不得把 AI 的推断当成用户已确认。只问"答案会真正改变结果"的问题，不为少问替用户默认。
7. 用户明确同意实际已展示题目或本批问题的推荐项时，按其回复实际指向的范围采用推荐；“用推荐的 / yes / 你定 / 下一步”须结合对应题目判断，不扩大为未来未展示问题的授权。笼统的“别问了 / 剩下你定”不能跳过尚未问清的关键设计决定，应说明问题用途和推荐依据，再请用户判断；对已明确同意的推荐不重复确认。纯实现方法由 AI 依据已定约束选择，不把技术细节变成新问卷。

### I.2 必问维度清单（防漏检查器，不是问卷脚本；N = 本期核心功能数）

> 下面这些维度是**防漏检查器**——用来自检"有没有漏掉某个会让本期交付跑偏或让未来发生重大返工的维度"，**不是逐条机械念一遍**。结合这个 PRD 的上下文整体判断哪些是真缺口、针对性地问；已明确确认的按 I.1 第 6 条继承。**绝不为省事替用户默认，也绝不为问而问。** 轮次编号仅作组织示意，不规定串行顺序；互不依赖的维度同轮收集。本期功能按实际缺口深问；范围外未启动功能只确认页面地图、依赖和不可逆约束，不追问页面状态与实现细节。

#### 组 ① 定盘子（先满足对应功能设计所需的骨架依赖）

- **轮 1 · 端形态 & 响应式 & 工作台**：做哪个端（PC 后台 / 移动 / 双端 / 小程序）？要不要响应式、断点怎么分？**登录后第一屏的工作台聚合什么**（这是不属于任何单一功能的聚合页，最常被忘）。
- **轮 2 · 信息架构 & 导航 & 站点地图**：全站怎么分区、导航模式（侧栏 / 顶栏 / 标签栏 / 面包屑）？**这一轮直接产出"页面互相调用关系"的骨架**——后面每个功能的页面都挂在这张地图上。

#### 组 ② 定人

- **轮 3 · 角色 / 权限 / 账号体验**：账号体系和认证方式必须直接读取 PRD/requirements，不得在设计阶段重新选择；若只写了“注册/登录”却没有明确采用既有系统、第三方认证、密码或其他方式，暂停相关设计并交回 prd-master 补齐，其他无依赖事项继续。这里只确认已定认证方式的页面呈现、登录态/恢复路径，以及角色在同一页面的能力差异（隐藏 vs 置灰），不得增加没有 REQ 的短信验证码、密码找回、第三方登录或注册入口。

#### 组 ③ 深定本期功能（覆盖每个本期核心功能，按缺口组织轮次）

- **轮 4 … 轮 (3+N)**：逐个核对本期核心功能，对尚未确认的设计先讲"我从 PRD 判断这个功能该拆成这几页（如列表页 / 详情页 / 编辑页）"，给通用拆法 + 推荐，用户拍板 → 落该功能的页面 + 每页骨架 + **适用的空 / 加载 / 错误 / 无权限状态**。已确认的同类规则直接继承，有业务差异再单独讨论。

#### 组 ③.5 扫描后续阶段的不可逆约束

- 范围外未启动阶段仍进入全量页面地图，但不逐页确认字段、状态、交互或高保真。
- 只问：如果现在忽略它，是否会让本期的数据模型、租户/权限边界、公开 API、核心状态机、导航骨架或外部集成产生高成本且难兼容的返工？
- 若会，只在蓝图与技术方案中定义最小扩展边界；若不会，登记为 `planned`，留到对应阶段再深设计。不得以“以后可能需要”为由提前建设。

#### 组 ④ 定体验（横切，定一次全站生效）

- **轮 (4+N) · 三大通用交互范式**：列表（分页 vs 无限滚动 / 搜索筛选排序 / 批量操作 / 导出）、表单（校验时机 / 必填标记 / 自动存草稿 / 离开拦截）、反馈（Toast / 弹窗确认 / 站内信通知）。
- **轮 (5+N) · 视觉风格**（= 原 design-master 整套，一次问清）：明暗模式 / 风格定调（Linear 科技 SaaS · Apple-Rams 极简 · 科幻 HUD · 其他）/ 设计 Category（14 类之一）/ 情绪基调 / 交互哲学（阴影提升 · 色彩响应 · 物理位移，全站统一不可混搭）/ 字体气质 / 设计签名（截图给外人能认出是哪个产品的那一笔）。按完整且容易判断的风格方向组织选项，不把每个术语拆成一题；可与设备、品牌等独立信息同轮收集。

#### 组 ⑤ 定后端与安全（只问需要用户决定的约束）

内部框架、实现方法和测试技术由 AI 依据已确认需求选择；仅缺少影响业务行为、成本、现有系统兼容或账号资源的关键约束时请用户决定，已确认的约束直接继承。

- **轮 (6+N) · 数据与集成**：核心数据实体有哪些？要对接哪些外部系统（如企业微信 / 小鹅通 / 飞书 / 本地素材库）？数据**用 API 方式还是后台直连数据库**？同步是实时还是定时？这里只细化已确认的接入方式；配置责任缺失必须回 PRD，不能在设计阶段补产品范围。
- **轮 (7+N) · 技术栈 & 架构 & 部署**：前后端框架取向、托管/部署方式、**国内可达性硬约束**（禁止推荐国内无法稳定访问的海外托管，见 `技术方案架构.md` 铁律 7）。锚定本期 scope，不为未启动范围过度设计。涉及文件存储时，按单/多实例、磁盘是否持久化、文件规模、直传/CDN 和备份目标判断；单实例且持久化磁盘足够时，默认服务器本地持久化目录，不自动引入对象存储。
- **轮 (8+N) · 安全 & 运维**：认证安全（二次验证 / 登录态）、敏感数据脱敏、**数据库要不要备份、自动还是定时**、**审计 / 日志做到什么程度**、危险操作可逆性（软删 / 回收站 / 撤销）。用户可见部分（如"我的登录设备"、审计日志查看页）落成页面，后端机制落进技术方案。

#### 组 ⑥ 收尾

- **蓝图确认**：在 I.3 展示**全产品页面地图 + 本期页面施工图范围 + 视觉方向 + 技术架构 + 后续不可逆约束**，区分已有依据的范围与实际阻塞项，确认当前可执行部分；不在这里和 I.3 各确认一遍。

### I.3 沉淀《设计决策蓝图》并最终确认

通过 Design 主入口的完整有效上游检查后，把以上决策汇总写入并展示 `{项目名}/output/设计决策蓝图.md`，用 AskUserQuestion 确认其中已具备依据的设计范围。§1 的 scope 与有效 requirements 同步；用户明确改变阶段范围时先按主入口回交 PRD 更新来源，之后只更新新增或改变的设计，不重问已确认 scope。上游门槛未通过不能先生成蓝图或设计产物；进入 Design 后，本阶段未决项在同一蓝图标明受影响 ID、缺口与依赖，只暂停这些部分，无依赖且已展示获确认的设计可先生成 MD/HTML。不能用待定项冒充完整蓝图；若未知会影响全局导航、角色、数据结构或视觉方向，相关共用设计也须等待。已在同一对话展示且获确认的总蓝图直接继承，方案/本期范围确认不能替代这次可见蓝图确认。

**进入阶段 II 前的确认条件**：待生成部分对应的蓝图已展示并获确认，需求、共用规则及其依赖明确，才能生成该部分详细设计。实际未决项回到 I.2 补问，不暂停无依赖的已确认部分；全局未知则阻塞所有受影响部分。完整交付仍须覆盖全部本期 scope，不能因已完成一部分或问了多轮就收尾。

**闸门满足后，按已确认范围连续执行阶段 II，中间不重复询问已确认事项。** 这份蓝图是阶段 II 所有规范的方向输入；明暗、风格、选型和拆页等决定一律使用已确认方向及约束。纯实现方法由 AI 自主选择。剩余设计决定补齐时更新同一蓝图，只确认新增或改变的部分；始终依据入口已核验的完整有效上游及真实 ID/revision，来源变化时按主入口回交所属 Master 修正并重新检查，不以部分输入代替完整来源。新设计歧义只暂停受影响部分，重大上游依赖按主入口回退规则处理。
