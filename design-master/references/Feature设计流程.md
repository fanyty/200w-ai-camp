# Feature 设计流程

仅在新功能或 Feature 增量设计时读取。项目定位、运行环境、链路衔接和共同边界见 `../SKILL.md`；下列流程按真实依赖推进，各环节只读取对应参考规范。

## 阶段 0 · 读取上游契约

1. 正式设计前按主入口统一检查，读齐同一项目完整的 `PRD详细版.md + requirements.md + requirements-analysis.md`，核实必要确认、范围、稳定 Source ID 与 revision 有效一致；有效产物和已有确认直接复用。缺失、未确认或过时则暂停正式设计，明确缺口，读取实际 prd-master 的 `SKILL.md` 并切回该阶段补齐，按其规则处理更早阶段的缺口；重新通过入口检查后再开始 Design。其间只可只读调查和整理已有证据，不倒填需求契约、不自造确认，不以并行准备先生成正式设计产物。
2. 从有效 `requirements.md` 读取 `workflow_mode`、revision、`scope` 与已建立的稳定 REQ/AC/NFR ID，最终纳入全部 active ID。按主入口的 scope 规则区分本期与范围外条目，已有交付契约可辅助恢复；用户明确调整范围时，由 PRD 更新 requirements，Design 更新蓝图与设计，TDD 更新验收契约，各自按实际 Skill 执行，保留每条需求原 Stage，不把阶段二继续当作未启动。口头已确认但尚未写入上游契约的信息仍须回 PRD 落实，不能由 Design 倒填。从完整有效的 PRD 和已确认业务输入提炼会影响设计/技术/安全的信号：
   - **产品形态与端**：大屏 / 桌面 Web 后台 / 手机 App / 小程序 / 嵌入式；单端还是多端。
   - **行业与品类**：映射到设计 Category，并提供技术选型约束。
   - **核心功能清单**：区分本期与范围外条目；本期核心功能数 N 用于核对覆盖，实际提问轮数取决于待澄清的缺口。
   - **业务闭环**：每条已确认流程的输入 → 处理 → 结果，以及角色、多端、渠道、接口与异常边界；不因并行推进删减或后置已确认内容。
   - **用户与角色**：谁用、几种角色、B 端冷静掌控还是 C 端温暖。
   - **数据与外部系统**：核心数据实体、要对接哪些既有系统（如企业微信 / 小鹅通 / 飞书 / 本地素材库）。
   - **方案前置能力**：逐项读取状态、负责人、证据或截止时间、替代方案、所属阶段和关联 REQ。
   - **外部能力配置责任**：逐项读取凭据归属、配置角色、`Surface`、`Scope`、生命周期、所属阶段和关联 REQ。
   - **阶段路线图（§0）**：保留原始阶段身份，页面深度和选型锚定本次已确认 scope；首次默认 MVP。
3. **前置能力与外部配置回退门禁**：PRD/requirements 进入当前阶段的已选方案依赖认证通道、第三方平台、移动应用正式分发账号/签名、支付、推送、硬件或资质，却没有已确认的 `Capability prerequisites`，读取实际 prd-master 的 `SKILL.md` 并切回该阶段补齐；当前已选方案实际采用 LLM、支付、短信、邮件、地图、对象存储等外部能力，却没有明确配置责任或责任表仍写 `none`，同样处理。能力词只用于提示核对；明确排除、方案对照或未启动阶段中的提及不触发本期回退。上游恢复完整有效前暂停正式设计，只读调查与证据整理可继续；直接承接同一项目的上游修订后重新核验，不要求用户重开流程或重复确认有效内容。禁止在设计阶段假设资源已经具备、改选账号密码、环境变量或管理后台。`onboarding/settings/admin` 必须有关联 REQ 并进入对应阶段页面地图；`deployment-secret` 只进入技术方案，不生成配置页。

## 阶段 I · 苏格拉底多轮互动决策

通过阶段 0 的完整有效上游检查后，读取 `references/提问收敛闸门.md`，按其中的沟通方式、设计维度和模板形成并展示 `output/设计决策蓝图.md`，由用户确认待生成部分及其共用规则后进入阶段 II；Design 内部的未决项只阻塞受影响部分，不能把未通过的上游入口检查降为局部未决项。已确认事项直接继承；只对影响结果的缺口继续提问。对已展示推荐的明确同意按实际范围采纳；笼统的“你来定”“别问了”不能跳过未问清的关键决定，对仍需用户判断的事项给推荐、理由和问题用途，继续必要澄清。已展示且获确认的同一蓝图不因切换 skill 再确认。

先按主入口的 UI 适用规则判断本期影响；无新增或受影响 UI 时，蓝图只记录必要的非视觉决策，省略页面地图、交互与视觉章节，不提问风格，不生成“不适用”占位内容。

## 阶段 II · 持续产出（先有整体初版，再按实际问题完善）

严格按各 `references/` 规范执行；凡规范里需要默认决策的地方，一律改用《设计决策蓝图》已定结果。不得新增蓝图未确认的外部服务、付费资源、平台账号或部署依赖；确实需要时按阶段 I 回退规则处理。

**自顶向下、逐步求真**：从已确认的核心流程、适用的页面地图和共用规则出发，尽快生成覆盖本期全貌的可查看初版，直接写入最终路径。已有产物即可展示并说明未完成处，不等全部配套材料收尾。随后在原文件中修正实际问题、补齐约定范围与交付标准，达标即交付；展示不增加审批，新的业务取舍仍须用户拍板。

步骤 1–6 仅用于本期新增或受影响 UI；无 UI 影响时直接完成步骤 7–8，保留技术设计、业务异常与真实验证面。

### 步骤 1 · 出页面清单（按 `页面清单规划师.md`）
- 输入：`PRD详细版.md` + 蓝图（§2 站点地图 + §4 各功能页面拆解）。
- 阶段衔接：页面清单"所属阶段"从来源 REQ 的 Stage 与 PRD §0 阶段路线图继承，同一实际页面跨阶段沿用一行和稳定 PAGE ID，可用逗号列出多个相关阶段，**覆盖全阶段、本期页排最前**。范围外未启动页面或同页未来能力在“功能范围描述”中写清 `planned + 前置依赖 + 与本期关系 + 功能范围`，只用于产品地图、报价和依赖规划，本轮不生成其详细设计；已有且未变化的页面保留实际产物。
- 产出：`{项目名}/output/页面清单.md`。

### 步骤 2 · 出 DESIGN.md + tokens.css（按 `设计系统设计师规范.md`）
- 输入：`PRD详细版.md` + 蓝图（§6 视觉风格锚点）。规范"战略分析流"的明暗/风格判断直接采用蓝图已定结果。
- 产出：`{项目名}/output/DESIGN.md` + `{项目名}/output/tokens.css`。先落盘页面需要的共用规则与 Token，设计说明可随页面补齐；规范完整性条目约束最终交付，不作为初版落盘和展示的门槛。

### 步骤 3 · 写本期每页 PRD 文档（按 `references/页面模板.md`）
- 按已确认 scope 与 `页面清单.md` 的“所属阶段”交集选页，每个 PAGE ID 只选一次，不固定只读阶段1。更新同一份当前有效页面，保留仍有效的既有行为；同页未启动阶段的能力只保留 planned 描述，不提前展开。范围外未启动页面不创建空文件。
- 依据页面清单当前行、对应 Source IDs 的需求和 PRD 语境、蓝图对应功能段及 `references/页面模板.md`，按实际内容组织新增页面的 `{项目名}/output/pages/{PAGE-ID}.md`；已有 PAGE ID 的真实产物沿用原路径。该页已确认的内容与流转足以生成初版时即可交给 HTML，文档细节继续补齐；未知业务不能猜。相关来源按需读取，不为每页重复分析全产品。

### 步骤 4 · 出本期每页高保真 HTML（按 `页面HTML规范.md`）
- 前置：该页使用的共用设计规则与 `tokens.css` 已就绪，未完成的设计说明不阻塞初版。
- 不等待全部 MD 完成：读对应页面 MD + `DESIGN.md` + `tokens.css` → 新增页面按同目录、同主文件名生成 `{PAGE-ID}.html`；已存在且身份唯一的 MD/HTML 配对沿用真实路径。HTML `<head>` 同时写入该 MD 元信息中的 `<meta name="page-id" content="PAGE-...">`。不得为范围外未启动的 `planned` 页面补空壳原型。

### 步骤 5 · 串联 + 一次本地链接目标扫描（按 `页面串联器.md`）
- 对本轮生成或更新的全部本期 HTML 执行一遍，按蓝图 §2 的调用关系和 PAGE ID 对应的真实路径接线；跨阶段指向已有真实页面时沿用原路径。完成后只批量扫描一次所有本地 `.html` 跳转目标是否真实存在。指向未启动 `planned` 页面但目标尚未生成的入口不注入假链接，在汇报中列明。**只接线不加件。**

### 步骤 6 · 按需展示设计系统
- 用户要求，或实际需要单独比较、确认共用组件风格时，读取 `设计系统展示页规范.md`，根据 `DESIGN.md` + `tokens.css` 生成 `{项目名}/output/design-system-showcase.html`。内容围绕需要展示的共用规则、组件及其真实状态组织；本期页面原型已足够展示时跳过此项，不为每个 Feature 额外交一份展示页。

### 步骤 7 · 出技术方案（按 `技术方案架构.md`）
- 输入：`PRD详细版.md` + 蓝图（§7 数据集成 / §8 技术栈 / §9 安全）。
- 锚定本期 scope、不为未启动范围过度设计（铁律 8）；国内可达硬约束（铁律 7）；**版本与维护状态按技术方案规范从项目环境或官方发布来源核实，区分已安装版、兼容版本与当前稳定版，不从训练数据推断**。
- 生成前对比蓝图与拟采用的全部外部服务、付费资源、平台账号和部署依赖：蓝图未确认的不得写入技术方案，必须退回阶段 I 确认并更新蓝图后再继续。
- 产出：`{项目名}/output/技术方案.md`。结构、推荐一致性等条目在生成时直接满足；版本、维护状态、国内可达性和新增外部依赖属于外部事实，仍须在写入前真实核实。

### 步骤 8 · 汇总完整设计追溯矩阵

- 收口时读齐真实完整的 `PRD详细版.md + requirements.md + requirements-analysis.md`，结合已确认蓝图与全部产物核对最终范围、ID、revision 和业务输入 → 处理 → 结果。不能因前期只读到部分需求而遗漏后续成文内容；发现变化只更新受影响设计，不重做无关部分。
- 按 `references/追溯与增量同步规范.md`，为每个 active REQ/AC/NFR 建立 `设计追溯矩阵.md` 行：本期映射稳定 `PAGE/CMP/API/DATA/SEQ/DEC` ID、真实详细产物、验证面与 revision，状态为 `covered/preserved`；范围外未启动内容至少映射页面清单/蓝图/扩展预留中的真实骨架和依赖，状态为 `planned`，已有且未变化的真实设计保留。
- 本期的关键跨组件业务流必须有 Mermaid sequence diagram；状态型实体必须有状态迁移或等价明确描述；所有异常行为必须指向错误处理落点。未启动范围除非属于已确认的不可逆约束，不提前展开这些施工细节。
- 保留完整七列 `Source ID / Source Revision / Design IDs / Artifact / Error/Invariant / Verification Surface / Status` 作为 TDD 输入，但不在 Design Master 内运行追溯校验脚本或第二轮覆盖验收。
- 仅增量运行输出 `change-impact.md`；只重生受影响项，未受影响 ID 和用户已确认决策保持不变。

> 按实际依赖推进：2、3、7 可并行；4 仅依赖共用设计规则与对应页面内容；5 依赖本轮 HTML；8 随各产物记录，交付前汇总。

---

## 阶段 III · 汇总交付

阶段 II 本期适用产物完成后，按主入口的产物契约汇总完整交付；本轮有 HTML 生成或更新时须完成一次本地链接目标存在性扫描。初版应已提前展示，不能到最终汇报时才首次提供查看入口。

给出实际本期产物入口和修改方式；有 UI 时让用户能查看并走通原型流程，生成了 `design-system-showcase.html` 时一并提供其入口。汇报 scope、实际适用的页面数量与链接扫描结果、不可逆扩展约束，不把“尚未深设计”的未启动范围或不适用的 UI 产物报告成缺失。明确下一步是 TDD，提示回复“继续，进入 TDD”；已授权继续推进时按主入口直接交接，不等待重复口令或新增阶段审批。
