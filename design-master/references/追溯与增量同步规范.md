# 追溯与增量同步规范

## 稳定设计 ID

| 类型 | 格式 | 例子 |
| :--- | :--- | :--- |
| 页面 | `PAGE-Fnn-nn` | `PAGE-F03-01` |
| 组件 | `CMP-Fnn-nn` | `CMP-F03-04` |
| 接口/契约 | `API-Fnn-nn` | `API-F03-02` |
| 数据实体 | `DATA-Fnn-nn` | `DATA-F03-01` |
| 时序/流程 | `SEQ-Fnn-nn` | `SEQ-F03-01` |
| 设计决策 | `DEC-nnn` | `DEC-008` |
| 修复点 | `FIX-BUG-nnn` | `FIX-BUG-001` |

发布后不重编号、不复用。语义变化递增 revision；拆分时旧 ID 标 retired，新 ID 写 supersedes。

## `设计追溯矩阵.md` 固定格式

```markdown
# 设计追溯矩阵

| Source ID | Source Revision | Design IDs | Artifact | Error/Invariant | Verification Surface | Status |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| AC-F03-01 | 1 | PAGE-F03-01, API-F03-02, SEQ-F03-01 | pages/PAGE-F03-01.md; pages/PAGE-F03-01.html; 技术方案.md §4 | duplicate_email → 明确错误；不得建重复记录 | component + integration + e2e | covered |
| AC-F08-01 | 1 | PAGE-F08-01, DEC-012 | 页面清单.md; 设计决策蓝图.md §4 | 阶段2依赖MVP账号主体ID保持稳定 | 阶段2启动时重新深设计与校验 | planned |
```

Feature 的 active `REQ/AC/NFR` 必须各至少一行；Bugfix 的 active `REPRO/CUR/EXP/UNCH/CON` 必须各至少一行。`Design IDs`、`Artifact`、`Error/Invariant`、`Verification Surface` 不得空白或 TBD。一个设计 ID 可以覆盖多个来源，但来源语义不得被合并丢失。

`Source Revision` 使用该来源条目的 `Revision`；AC 未单列时继承 Parent REQ 的 Revision，Bugfix 条目未单列时继承其 Metadata revision。最终矩阵须与当前来源一致，不得只沿用旧 revision 或把 `stale` 当成完成；TDD 的 `source_revision` 则填写整个上游契约的 Metadata revision。

Feature 按 requirements 与蓝图一致的 `scope` 控制本期设计深度；继承主入口的阶段等价规则，缺省首次 MVP，阶段变更不改写条目 Stage：

- `REQ` 的 `Stage` 与 scope 中任一已确认阶段匹配时属于本期；`AC` 继承 Parent REQ 的阶段。编号阶段按编号精确匹配，实际阶段名称按完整名称匹配，不以包含 `MVP` 或阶段字符串子串代替范围判断。
- `NFR` 若未声明 `Applies-to`，视为全局并进入本期；若声明，则只要关联任一本期 REQ 就进入本期。
- 页面清单允许同一 PAGE ID 关联多个阶段；scope 与其“所属阶段”有交集时选取一次当前页面，但每条 source 的本期归属仍按自身 Stage 判断。同页未来 source 仍为 `planned`，不得因页面已有 MD/HTML 就宣称其行为已覆盖。
- 本期 source 状态必须为 `covered` 或增量未变化的 `preserved`，并指向页面文档/高保真、技术方案、API/DATA/SEQ 等真实详细产物。凡 `Design IDs` 含 `PAGE-*`，`Artifact` 必须写该页面**实际存在**的 MD 与 HTML 路径，不得只写通配符或页面显示名称。
- 新增页面规范位置为 `output/pages/{PAGE-ID}.md` 与 `output/pages/{PAGE-ID}.html`。既有产物按 MD 元信息与 HTML `meta[name="page-id"]`（缺少该元信息时可用标题/正文）确认属于同一 PAGE ID，身份唯一则记录并沿用实际路径，仍可 `covered`，不强迁移、不重复生成，也不得仅因名字不同伪报缺失。零匹配、多匹配或内容身份冲突才阻塞。
- 范围外未启动 source 可以为 `planned`：必须有稳定 Design ID，并指向 `页面清单.md`、`设计决策蓝图.md` 或 `技术方案.md` 的真实骨架、依赖或扩展预留；不得伪造已经完成的页面文档、高保真或接口。
- 范围外已有真实且仍有效的深度设计可以保留 `covered/preserved`，但不得为了让状态好看而提前扩张产物；用户启动该阶段后，本期条目须由 `planned` 补齐为真实详细覆盖。
- Bugfix 没有“以后再设计”的安全空间，全部 active source 仍必须 `covered/preserved`。

本期关键业务流用 Mermaid sequence diagram 并分配 SEQ ID；状态型实体给出合法迁移、非法迁移与并发冲突；本期 NFR 必须映射测量点而非只写“技术方案已考虑”。范围外 `planned` 项只记录会约束本期的依赖和不可逆边界，等对应阶段启动时再补完整流程与测量点。

## 矩阵填写规则（写入时直接满足）

1. 每条 active source ID 直接写入真实设计落点：本期是施工级落点，范围外未启动内容是可追踪的 planned 骨架，已有设计按证据保留。
2. 每个页面/API/数据实体直接写明来源 ID；无来源项标 `design-derived` 并说明必要性，不得伪造需求。
3. 本期的所有错误与不变行为直接写明实现面和验证面；未启动范围至少写清依赖或不可逆约束，以及何时重新深设计。
4. 矩阵不得写入 `missing / TBD / stale` 的交付状态；本期不得写 `planned`。范围外合法 `planned` 不阻塞本期进入 tdd-master。

这些是矩阵首次生成时必须满足的内容约束，不触发 Design Master 内的第二轮覆盖校验；真实验收由下游 TDD master 承担。

## 增量同步

比较 source ID 的 revision，输出 `change-impact.md`：

```markdown
| Changed Source | Old→New Revision | Affected Design IDs | Artifacts | Action | Status |
| AC-F03-01 | 1→2 | API-F03-02, SEQ-F03-01 | 技术方案.md; 注册页.md | regenerate + review | stale |
```

只把直接映射和依赖闭包标 stale。未受影响设计 ID、已确认视觉决策与文件保持原状。修复并复核后更新矩阵 source revision：本期恢复为 `covered/preserved`，范围外骨架恢复为 `planned`（已有真实且仍有效的深设计可为 `covered/preserved`）；禁止仅改 revision 数字而不检查行为。scope 扩大时补齐新纳入条目的详细设计，不把旧 `planned` 直接改为 `covered`。
