# 设计大师 · design master

把已确认需求转为可直接开发的设计交付：技术方案和需求追溯，以及实际 UI 范围需要的页面骨架、本期页面与原型、设计系统；Bugfix 只设计证据证明受影响的修复面。设计完成后进入 tdd-master 生成验收契约，再衔接 `/goal` 开发与验收。

## 产物与边界

正式开始 Feature 设计前，必须读取并核查同一项目完整的 `output/PRD详细版.md`、`requirements.md` 与 `requirements-analysis.md`：已由 prd-master 完成交付，并有其已通过 Solution 前置检查的可核验依据，必要的用户确认有效，范围、稳定行为 ID 与 revision 一致且未过时。已有有效核验可复用；缺少交接依据先回 PRD 核查，已知缺少 Solution 前置不得放行。Bugfix 则核查完整有效的 `bugfix.md` 及其确认、复现与修复范围，不要求补造 PRD。文件存在、用户点名 Design 或要求继续都不能代替入口检查；缺失、未确认或过时的处理见下方“定位项目与选择模式”。

**本期范围 `scope`**：继承 `requirements.md` Metadata 中逗号分隔的已确认 Stage 值；旧契约未声明时默认 `MVP`。`MVP`、`阶段1(MVP)`、`阶段1`（含中文编号“阶段一”）视为同一阶段；其他编号阶段按编号精确匹配，`阶段2` 不匹配 `阶段20`；“试点期”“全量交付”等已确认名称按完整名称匹配，不强制改名或编号。用户明确启动阶段二等新范围时，先读取实际 prd-master 的 `SKILL.md` 并切回该阶段更新上游 `scope`；重新通过入口检查后，Design 同步已有设计决策蓝图 §1 与受影响设计，再由 tdd-master 同步验收契约，不代写其他阶段产物，不改写需求条目的 `Stage` 身份。已有交付契约可辅助恢复范围；范围外未启动内容保持 `planned`，已有且未变化的真实设计保留，不新增范围文件或流程。

Feature 产物均写入 `{项目名}/output/`：

以下 UI 产物按真实需求和影响适用。本期没有新增或受影响 UI 时，不生成页面清单、设计系统、Token、页面 MD/HTML 或展示页，也不做链接扫描；已有 UI 产物保留。仍在同一份设计决策蓝图中记录必要的非视觉决策，完成技术方案与全部来源追溯，不为不适用项创建空文件。本期存在页面、交互或可见状态变化时，必须完成对应 UI 设计，不能因主要改动位于后端而豁免。

```text
output/
├── DESIGN.md                       ← 本期共用设计规则、理由与可复用 CSS
├── tokens.css                      ← 56 个 CSS 变量契约
├── design-system-showcase.html     ← 按需生成的共用风格与组件展示页
├── 页面清单.md                      ← 全量页面与调用关系（本期排最前）
├── 设计决策蓝图.md                  ← scope + 全产品骨架 + 本期深度决策 + 后续不可逆约束
├── 设计追溯矩阵.md                  ← 本期=covered/preserved；未启动范围=planned
├── change-impact.md                 ← 上游 revision 变化导致的 stale/重生范围（有变更时）
├── 技术方案.md                      ← 8 段技术方案（按影响选型 + 明确推荐 + 国内可达）
└── pages/
    ├── {PAGE-ID}.md                  ← 本期新增页面：按实际内容组织的产品需求文档
    └── {PAGE-ID}.html                ← 同一 PAGE ID 的高保真 HTML（串联后可点击走流程）
```

新产物以稳定 PAGE ID 唯一命名（如 `pages/PAGE-F01-01.md` 与 `.html`）；端、阶段、模块和展示名称保留在页面内容与清单中。同一实际页面跨阶段演进沿用 PAGE ID 与一份当前有效的 MD/HTML；页面清单的“所属阶段”可用逗号列出其来源需求的多个阶段，与 scope 有交集时纳入本期一次，不改变各 REQ 的单值 Stage。既有页面按 MD 页面 ID 与 HTML `meta[name="page-id"]` 确认实际路径后沿用，不为命名统一强迁移或生成第二份；既有不同 PAGE ID 不因同名自动合并。

设计系统展示页仅在用户要求，或实际需要单独比较、确认共用组件风格时生成；本期页面原型已足够展示时无需额外产出。

Bugfix 模式改为输出 `修复设计.md + 设计追溯矩阵.md + change-impact.md`，仅在受影响 UI/接口确需更新时修改对应页面文档或技术方案。

本阶段只负责设计产物。高保真原型和用于核实设计选择的必要技术小试属于本阶段工作，不扩为产品实现；不代写 PRD/bugfix 需求契约、TDD 验收契约或生产实现。

## 链路衔接与已有上下文

- 沿同一项目的实际进度承接 PRD/bugfix 契约、共享对话、已确认业务输入与已有产物，只补会改变设计的缺口，不从零重做已确认产物，不让用户重新介绍项目或复制背景。已有代码可用于核实现状、复现和约束，不能替代需求确认或补造设计决定。
- 默认沿 Solution → PRD → Design → TDD → `/goal` 推进，设计交付后必须说明下一阶段和继续方式；对应阶段入口条件满足且已授权继续推进时直接衔接，不新增阶段审批。用户明确暂停、终止或要求本轮只修改当前文档时遵从，在既有状态中保留实际停点与未通过项，不视为入口通过或整条链路完成，不新增 `workflow_mode`、上下文或状态文件。
- 入口检查通过前只可只读调查和整理已有证据，包括已提供的端形态、设备约束、品牌素材与风格偏好；不能以并行准备为由先生成蓝图、技术方案或其他正式设计产物。有效上游和已有确认直接复用，不重复提问。
- 入口检查通过后，可见蓝图中待生成部分仍须用户确认后才据此展开详细设计。方案/本期范围确认不能替代蓝图确认；蓝图若已在同一对话实际展示并获确认，直接复用。以已核验的真实完整上游契约维持追溯与一致性，后续来源变化时重新核对影响，不以先行草稿代表完整交付。

## 路径与运行环境

- 把当前 `SKILL.md` 所在目录记为 `SKILL_ROOT`。参考文件从 `SKILL_ROOT` 解析，不假设用户工作区另有 `design-master/` 源码。所有 `output/xxx` 一律相对当前项目目录。
- 页面模板直接用 `references/页面模板.md`，不要求项目根目录另放一份。设计追溯在生成时按规范填写，交接时由 TDD 的交付校验统一核对。
- `AskUserQuestion` 指当前环境的结构化提问能力；遵守工具容量，工具不可用时用同样结构的纯文本提问。
- 子 Agent 按独立任务需要使用，不固定每页派一个；本期页面、角色与产物保持完整。

## 定位项目与选择模式

1. 优先使用当前对话已定位的项目目录；尚未定位时扫描工作区下含 `output/requirements.md` 或 `output/bugfix.md` 的目录，多个且上下文不能唯一确定时让用户选择。先按“产物与边界”核验本次工作类型的完整有效上游。缺失、未确认或过时则明确具体缺口，暂停正式设计，从当前环境定位实际所属 Master，读取其 `SKILL.md` 后切换到该阶段补齐；必要时沿其规则追溯更早阶段。不得以 Design 身份倒填需求、改写上游契约或自造确认；补齐后重新核验，再回到 Design。所需 Skill 不可用时如实报告，不凭名称模拟。
2. 意图是修复且有 `bugfix.md` 时，读取 `references/Bugfix设计规范.md`：产出根因证据链、最小修复面、UNCH/CON 保护、验证面与回滚方案。不要求 PRD，不加载无关 Feature 规范；仅更新受影响页面、接口或技术设计。
3. 入口检查通过后，新功能或 Feature 增量设计读取 `references/Feature设计流程.md`，按可见蓝图确认、阶段内依赖、持续生成和最终收口推进。
4. 上游 revision 变化时，按 `references/追溯与增量同步规范.md` 先输出 `change-impact.md` 并标明受影响项 `stale`；不全量重编号，不覆盖未受影响产物或用户决策。

## 共同约束

- **可见蓝图确认先于 Feature 详细设计**：已确认事项直接继承，已展示且获确认的同一蓝图不重复确认；方案/本期范围确认不能替代蓝图确认。未知只阻塞受影响部分。
- **保留苏格拉底互动**：影响设计的业务取舍和蓝图未决项仍须按提问收敛规范澄清；笼统的“你来定”“别问了”不能替代尚未问清的关键设计决定，应给出推荐、理由及问题用途，再请用户判断。对实际已展示题目或本批推荐的明确同意有效，不扩大为未展示问题的确认，已确认事项不重复提问。
- **按依赖持续推进**：互不依赖的问题批量收集，已就绪内容直接写入最终路径并展示，说明尚未完成处，继续在原文件补齐。新业务歧义或未确认的外部服务、付费资源、平台账号、部署依赖，只暂停受影响部分并补齐决策。
- **完整范围不削减**：全产品定骨架，本期出施工图，保留已确认的页面、角色、多端、渠道、接口与异常边界；未启动范围只记录 `planned` 骨架、依赖和真实不可逆约束，不提前生成详细页面或空壳原型。
- **真实来源与证据**：不编造业务事实、ID、路径或技术版本。没有稳定 Source ID 的页面/API 不自称来自需求；本期 active REQ/AC/NFR 必须 `covered/preserved`，范围外 active source 至少有真实 `planned` 骨架，已有设计按当前证据保留。
- **增量不抹历史**：只更新受影响项，不把旧 `completed` 状态默认继承到已变化的语义。各产物的具体生成规则保留在对应参考规范中，不再复制第二套。

## 交付与衔接

Feature 完成对应流程的本期适用产物后，汇总实际查看入口与交付 scope；本轮有 HTML 生成或更新时，完成一次本地链接目标存在性扫描并汇报结果。TDD 的输入包括完整 requirements、设计追溯矩阵、技术方案，以及适用的页面清单与本期每页真实 MD/HTML，scope 必须一致。

Bugfix 一次性汇报 `修复设计.md / 设计追溯矩阵.md / change-impact.md`，列明已确认根因证据、受影响产物、UNCH/CON 保护和回滚方案，不声称未实际验证的修复已生效。

交付时给出真实文件或页面的查看入口和修改方式，并说明：“下一步进入 TDD 大师，定义开发完成标准。有要调整的地方，告诉我具体页面或设计项；继续请回复‘继续，进入 TDD’。”用户已授权继续推进时，说明下一步后直接读取当前环境已发现的 tdd-master 的 `SKILL.md`，交接同一项目的真实产物并继续，不再等待口令、补抄背景或新增阶段审批。用户明确暂停、终止或本轮只改当前文档时遵从。

TDD 可只读预查已有证据；正式生成验收集合与契约前必须按其入口规则核验完整有效的上游，不能以提前准备绕过 Design 交付。
