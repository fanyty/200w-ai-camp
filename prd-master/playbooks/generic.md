# 通用调研 Playbook（冷门品类 fallback）

> 本文件是定向查证的资料入口，不是必做清单。只读取能回答当前未决问题的部分；不设竞品数量或数据项配额。已有证据足够即停止。下面的历史数值、市场判断与渠道只是线索，实际使用前必须查证来源、日期及适用范围，不能直接当成当前事实或产品门槛。

## 适用场景

不在 saas / mobile-app / ecommerce 三大主品类的项目：
- 硬件 / IoT / 智能设备
- 医疗 / 生物科技
- 金融 / 保险 / 资管
- 教育 / 培训 / 知识付费
- 制造 / 工业 / 供应链
- 政企服务 / 公共领域
- 内容创作工具
- AI 模型 / 算法服务
- 任何混合品类（如 SaaS + 硬件）

## 总原则

没有专用品类时，从当前业务疑点选择相关资料。证据要求不变，但不为覆盖品类而展开整套扫描。

---

## 一、按当前问题选择竞品

### 找法（通用）

按相关性顺序：

1. **联网搜索关键词组合**：
   - `{产品定位} alternatives`
   - `best {品类} {2026}`
   - `{知名头部产品} vs / competitors`
   - `{细分场景} solutions`
2. **垂直行业目录**：
   - 硬件：CES 获奖产品、Indiegogo/Kickstarter top
   - 医疗：FDA 注册产品、Pitchbook 医疗赛道
   - 金融：Fintech100、巴塞尔合规产品
   - 教育：得到/混沌/樊登/三节课等课程平台
   - 制造：阿里 1688、慧聪、行业展会获奖
3. **行业垂直媒体**：
   - 36 氪 / 虎嗅 / TechCrunch 按品类筛选近 1 年报道
4. **学术圈**：
   - 如果是技术驱动产品（AI 模型、生物科技等），arxiv + Google Scholar 找 SOTA 论文
   - Demo 站、开源 repo 也算"竞品"

### 记录

- 公司/产品 / 一句话定位
- 与当前问题相关的核心功能
- 商业模式（订阅 / 一次性 / 服务费 / 硬件 + 服务 / 混合）
- 用户规模或营收（按真实来源、日期与统计口径记录依据等级；找到网页不等于 A 级，找不到就标明未公开）

## 二、抓官网/产品页

用当前环境可用的页面读取能力查看：
- 主页（提取定位 + 价值主张）
- 产品/功能页（提取功能列表）
- 价格页（如有）
- 关于我们/团队（提取背景）

冷门品类特殊点：
- 硬件：抓产品规格表、官方测评、京东/天猫产品页
- 医疗：抓 NMPA 注册信息、FDA 510(k)、临床试验数据库
- 金融：抓产品说明书、风险评级、监管备案

## 三、挖差评（用户痛点的代用品）

### 通用渠道

| 渠道 | 通用性 | 覆盖品类 |
|------|--------|---------|
| 知乎"为什么放弃 XX" / "XX 缺点" | 高 | 全部 |
| 小红书"XX 测评" / "XX 踩雷" | 高 | C 端为主 |
| 微博搜品牌名 | 中 | 全部 |
| 黑猫投诉 tousu.sina.com.cn | 高 | C 端、有客服的 B 端 |
| Reddit 子版块（r/{品类}） | 中 | 海外为主 |
| 行业垂直论坛 | 高 | 因品类而异（如硬件 = Mobile01、医疗 = 丁香园）|

### 冷门品类专属

| 品类 | 挖差评的"非常规"地方 |
|------|--------------------|
| 硬件 | 京东问大家、贴吧、什么值得买 |
| 医疗 | 丁香园、医脉通、专业医生群 |
| 金融 | 雪球评论、东方财富股吧、私募排排网 |
| 教育 | 黑猫投诉、行业自媒体（如"芥末堆"）|
| 制造 | 阿里 1688 买家评论、行业展会反馈 |
| 政企 | 招投标平台中标后评估、政府采购年度评价 |
| AI 模型 | HuggingFace 评论、arxiv 引用 + 批评论文 |

### 挖什么

- 退货/取消原因
- 性能不达预期
- 体验差点
- 客服/售后差
- 性价比抱怨
- 合规/安全担忧

- 给出"如何自己测/采集 benchmark 的方法"
- 影响当前决定的未知写入 assumptions.md，按依赖确定验证时点；不能一律延后到上线

## 五、品类混合项目处理

### 情况 A: 主品类清晰、附带次品类

例：主品类是 SaaS，但附带一个手机端 App 模块。

**做法**：
- 主用 saas.md playbook
- App 部分参考 mobile-app.md 的差评挖掘和 benchmark
- 复用已有 evidence/ 材料；确有独立内容才增加 `mobile-app-addendum.md`

### 情况 B: 两个品类同等重要

例：硬件 + 配套 App + SaaS 后台（典型 IoT 项目）。

**做法**：
- 用本通用 playbook 作为主框架
- 只查每个品类中实际影响方案的未知；已有资料直接复用
- 资料确需分别维护时，再在 evidence/ 下按 `hardware/`, `app/`, `saas/` 分目录

### 情况 C: 完全新品类（罕见）

例：太空旅游、脑机接口等。

**做法**：
- 用通用 playbook，调研范围限定到"最接近的已有市场"
- 未找到公开资料时明确缺口，不因品类新就预先断言没有证据
- 影响判断的假设进入 assumptions.md，依据等级与风险由实际来源和后果确定
- 只有证据不足以支撑方向时，针对该疑点做战略复核

---

## 六、何时停止查证

当前问题已有足以支持判断的证据就继续方案；没有此类未知时不启动研究。来源冲突、监管或关键技术不确定性只加深相关问题，不按竞品数量判断充分性。没有公开证据时标明缺口及受影响决定；仅让依赖该证据的工作等待，不要求用户确认“调研是否足够”。
