# 阶段 5 PRD 写作与交付

基于已确认方案和本次范围，先把已定行为写入实际 `requirements.md`，再与完整 PRD 正文同步完善。默认由 Controller 或一位主笔完成首稿；内容复杂且章节可独立推进时才分工，不按角色数创建 Agent。

## 输入与模板

共同输入是已确认的 `proposal-v1.md` 及本次范围、`scene-anchor.md`、`assumptions.md`、`debate-log.md` 中实际处理记录，以及 `output/requirements.md` 的稳定 ID 和 revision。只读取与任务有关的来源，未触发调研不要求补齐竞品或 benchmark；已有明确决定直接继承，不因进入写作或缺少历史标题、状态字段而重新询问。

Feature 必须以同项目真实、已确认且仍有效的 `output/解题方案书.md` 及其状态/确认来源为写作前置；缺失、未完成或过时先切换 Solution 补齐，不能由 PRD 代写或用下游材料追认。按 `SKILL.md` 的“承接解题方案书”将确认的解法、数据约束和产品结果落实到对应正文与需求条目；委派写作时提供相关原文及其确认、假设状态，不能只给方案书文件名或转述摘要。交付前核对承接，输入仍有效时只修遗漏条目，不重做解题。复杂 Bugfix 使用既有专用规格链，不套用本 Feature 写作前置。

正文结构、章节编号和表格以 `templates/prd-{saas|app|ecommerce}.md` 中当前品类模板为唯一来源；其他品类选最接近的模板，按实际内容调整。角色文件只提供专业判断方法，不另造目录或复制章节骨架。沿用模板的 §0 标题，在其中表达本次已确认 scope、阶段划分和完成定义；用户已确认全部交付时，不以 MVP 概念削减范围。模板的行业例子、指标、数字和未来阶段不能变成新增需求。

所有参与者原样沿用同一份 `F / US / REQ / AC / NFR` ID；Controller 合并时统一章节引用，不为行文或校验重编号。专业分工如下，只加载实际参与者的文件：

| 主笔 | 内容边界 | 按需读取 |
|------|----------|----------|
| PM | 目标与收益、角色与故事、成功度量、产品验收条件、依据 | `agents/prd-author-pm.md` |
| 架构师 | 已确认行为所需的系统边界、数据关系、流程状态、架构取舍与外部依赖 | `agents/prd-author-architect.md` |
| 工程师 | 详细功能、交互状态、边界异常、实现风险与 AC 清晰度复核 | `agents/prd-author-engineer.md` |

PM 主笔 AC 的产品场景与可观察结果；工程师复核歧义、边界和异常结果。测试方法、工具、自动化策略、测试数据、覆盖率和回归方案由后续 TDD Master 定义，不在 PRD 写作或评审时向用户询问。

## 通用委派与复核

本小节适用于方案评审与 PRD 写作。阶段 4 的 Reviewer 只需读取本小节，不因此启动阶段 5 写作、校验或交付。

- **委派**：给出具体问题或章节任务、当前稿件、已确认 scope、相关来源、已有决定及输出位置。多主笔时明确“主笔 / 参与 / 不碰”的边界；共用已有事实与术语，不要求作者相互隔离。角色冲突由 Controller 处理，不凭角色增加任务。
- **独立评审**：Reviewer 首次判断不参考其他 Reviewer 的结论。只报告有位置、依据和实际后果的问题；结果说明检查范围、问题位置或 ID、证据、影响、建议与处理状态，无问题可以直接返回结论。不得编造来源、比例或角色发言，也不为填表制造问题。
- **修订与权限**：Author 修复有证据的遗漏、矛盾和实现分叉；Controller 对意见作接受、附依据驳回或待决处理。在既有授权内可消除的歧义直接修正；只有确实未决、会改变产品行为、范围或重大取舍的决定才保留 `OPEN_QUESTION` 交用户拍板，不能靠多数意见关闭。
- **定向复核**：仅当专业证据不足、合并有口径风险、问题未关闭或修订可能改变已检查结论时，追加相应 Reviewer 或 `agents/cross-chapter-reviewer.md`。只查受影响部分，已关闭问题没有新证据不重开；没有新问题即结束，不安排固定轮次或全员终审。
- **文件与记录**：仅在实际分工时使用 `drafts/r1-{pm|architect|engineer}.md`；确有复核或修订可沿用 `r2-*-reviews-others.md`、`r3-*.md`、`r4-cross-chapter-review.md`，不补齐不存在的轮次。实际问题与处置汇入 `debate-log.md`。

## 写作与收敛

方案与本次范围明确后，先用稳定 ID/revision 将已确定行为写入 `{项目}/output/requirements.md`，再同步完善 `{项目}/output/PRD详细版.md`；未知显式标明，不把初稿或未确认行为当最终契约。核心三份齐备、P0/P1 清零且必要检查通过后才交 Design；可预先做只读事实核查，不提前生成设计产物。

首稿覆盖完整已确认多端、渠道、接口和功能，保留目标、角色、范围、完整业务旅程、各功能结果，以及影响理解和决策的关键输入、边界、失败结果、风险与取舍。逐条条件和 AC 细则在 `requirements.md` 维护，PRD 的功能说明引用对应条目，不要求全文重抄；必要摘要仍保留，不能缩成纯 ID 索引。沿用现有功能清单和 US → F 映射，规则细则引用放在所属功能说明中。数字和价值判断保留来源或依据等级，假设注明依据与验证方法；缺少量化证据时写可观察结果和证据缺口，不反推数字。多主笔完成后由 Controller 立即整合完整首稿，解析交叉引用，不先安排全员互审。

落盘即在对话提供查看入口与“初版，待完善”的真实状态，继续处理具体问题，不额外等待批准。Controller 对照 scope 检查覆盖、可观察结果和跨章节口径，按上节处理实际缺口；风格偏好或不影响当前交付的建议不触发重写。

已确认内容完整、P0/P1 清零、必要校验通过且没有新的具体疑点时，交付核心文件。相同问题没有新增证据或修复进展时，定位根因或说明缺失的用户决定/外部证据，不以重复互审代替解决，也不把受阻标成完成。

## 输出纪律

- `PRD详细版.md` 直接使用品类模板的一级标题和正文结构，不在前后加入过程说明、客套或把整篇包入 Markdown 代码块。
- 正文保留产品行为、约束、结论与依据；专家辩论和阶段判断过程留在 `debate-log.md` 或实际草稿中。
- 对话提供实际文件入口和状态，不复述整份 PRD；环境不能写文件时才直接输出完整 Markdown，并如实说明未创建文件。
- `PRD-summary.md` 与 `PRD-dev.md` 按各自模板提炼，同样不夹带生成过程说明。

## 关键决策记录

跨章节冲突处理完成后，由 Controller 统一筛选关键决策。**只有同时满足下面 3 条，才进入 PRD 的「关键决策」表：**

1. 存在至少两个真实可行的方案；
2. 已由有权拍板者明确确认，或属于用户已明确授权 AI 决定的范围；产品方向、范围、成本、外部依赖或重大风险发生变化且没有相应授权时，仍由用户/负责人决定；
3. 未来推翻会改变核心产品边界、关键架构，或产生明显返工。

不满足闸门的普通选择只写在对应 PRD 章节。已授权实现范围内、不改变产品边界、成本、外部依赖或重大风险的技术选择由 AI 按证据决定，不新增技术负责人确认；确实超出授权的选型先写为「架构建议」并保留 `OPEN_QUESTION`，不能伪称已决定。完整讨论留在 `debate-log.md`，不要复制进 PRD。

通过闸门的决定只做两处最小记录：写入 `PRD详细版.md` 的一行关键决策表，并复用 `state.json.key_decisions_made` 保存结构化索引。**不创建独立 ADR/DR 文件。**`PRD-dev.md` 从详细版同步同一张表，不重新推导。

若该决定改变可观察行为、阈值、兼容性或约束，必须同步回写对应 `REQ/AC/NFR`；决策表只保存选择依据，不成为第二套需求事实源。设计阶段的 `DEC-*` 只编号设计层衍生决策，不替代或复制这里的产品/架构决策记录。

## 维护机器需求契约 `requirements.md`

按 `references/需求契约与模式路由.md`，先落盘已确定行为，再与 PRD 同步完善 `{项目名}/output/requirements.md`；不等全文定稿才首次生成契约：

- 功能行为与异常行为使用 EARS 语法；每个 US 必须声明有效 `Role`。`Metadata.scope` 记录本次已确认交付范围，REQ 的 `Stage` 保留实际所属阶段，不将全部需求改为 MVP。
- 按该规范保留 `Capability prerequisites` 与 `External capability configuration` 两表及其状态、证据和责任字段；本次范围的实际依赖不得写成未知后续项。首次引导、设置页或管理后台承担配置时必须有对应 REQ/AC，不能擅自改为部署凭据。
- 每个 AC 必须指向一个 REQ，每个 REQ 必须标所属阶段与状态 `active / retired`。
- `requirements.md` 是下游行为契约；PRD 是人类主文档。两者冲突时暂停受影响的下游项，回到来源修订并同步 revision，不得任选一份继续。无依赖的已确认内容可继续。

## 跨需求正确性分析

对完整需求集合执行 `references/需求契约与模式路由.md` 的六类分析，结合本次 scope 与跨阶段依赖判断实际影响，输出 `{项目名}/output/requirements-analysis.md`：逻辑不一致、含糊量词、约束冲突、未声明假设、缺失边界/失败/并发、不可验证指标。

- P0：需求集合不可同时满足或会导致安全/数据错误 → 必须同步修正 PRD 与 requirements，并复查受影响分析。
- P1：会造成实现分叉 → 先查现有需求、证据和已确认决定；在既有授权内可消除的歧义直接修正并回写两份文档。只有仍未决、且会改变产品行为或范围的业务选择才请用户拍板。
- P2：不影响本次 scope → 可登记为后续项，但必须有 ID 与理由。
- PRD 核心交付和 Design 接管前必须核心三份齐备、`P0=0`、`P1=0` 且必要检查通过；校验可随实际文件逐项运行。未决问题只暂停 PRD 内受影响项，同阶段无依赖的写作与只读查证继续；不提前形成 Design 蓝图，也不让 design-master 猜业务答案。

## 运行契约与结构检查

先按 `SKILL.md` 的「运行环境适配」取得 `SKILL_ROOT`，再选择当前平台可用的 Python 3.10+ 启动器：macOS / Linux 用 `python3`，Windows 用 `py -X utf8`。脚本必须使用 `SKILL_ROOT` 下的绝对路径，不能相对用户工作区查找。

```bash
python3 "<SKILL_ROOT>/validators/check_evidence.py" "{项目名}/output/PRD详细版.md"
python3 "<SKILL_ROOT>/validators/check_format.py" "{项目名}/output/PRD详细版.md"
python3 "<SKILL_ROOT>/validators/check_consistency.py" "{项目名}/output/PRD详细版.md"
python3 "<SKILL_ROOT>/validators/check_requirements_contract.py" "{项目名}/output/requirements.md" "{项目名}/output/requirements-analysis.md"
```
Windows 将每行启动器替换为 `py -X utf8`，并把 `<SKILL_ROOT>` 替换为实际安装目录；不要原样执行占位符。

`check_evidence.py`、`check_format.py`、`check_consistency.py`、`check_requirements_contract.py` 用于证据标注、结构和契约检查；失败时定位具体条目，只修受影响内容，并重跑失败检查及本次修改可能影响的检查。`check_format.py` 的接口、硬件和 SDK 提示需结合已确认需求判断，属于外部契约或兼容约束的内容必须保留；提示不阻断交付，退出码 2 才表示硬错误，不能为消除提示删除已确认接口。通过且没有新改动或具体疑点后立即交付核心文档，不为完成轮次重复运行。相同错误没有新证据或修复进展时，查根因并说明阻塞；不得靠反复改稿绕过校验或替用户补未确认决定。

`check_consistency.py` 对 ID 和章节的识别有局限；“未识别”或脚本 PASS 不代表需求语义一致，须结合跨需求正确性分析判断覆盖与冲突，不能改回旧 ID 迎合脚本。

## 核心交付与按用途提炼

`PRD详细版.md`、`requirements.md`、`requirements-analysis.md` 内容齐备、P0/P1 清零且必要检查通过后，PRD 核心完成，可直接交给 design-master。详细版按上述分工保留完整业务全貌、关键规则摘要、结论和依据；辩论过程只留在 `debate-log.md`。

仅在用户有对应阅读或交接用途时，在同一 `output/` 下生成浓缩版：

- **`PRD-summary.md`**（老板、投资人或跨部门汇报）：按 `templates/prd-summary.md` 提炼目标、收益、完整交付边界和关键取舍。
- **`PRD-dev.md`**（开发交接）：按 `templates/prd-dev.md` 提炼契约引用和关键边界；业务语境引用完整版，行为细则引用 `requirements.md`。

两份从核心文档提取，必要章节按实际内容覆盖，不凑行数、不再问已确认信息，也不重新推导范围。可并行或随后完成，不阻塞 Design/TDD。用户需要 PPT 时另读相关规范；摘要和 PPT 都不能反向决定核心是否完成。交付时只报告实际生成的文件及其状态。
