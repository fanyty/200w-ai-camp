# 目标、查证与方案形成

仅在 Feature 已形成明确共同理解，准备整理目标、定向查证或写方案时读取。启动与访谈不预加载本文件；已有确认原样继承，只处理实际未决问题。

## 阶段 2 · 整理目标与收益

从场景锚点和已有决定中整理“为谁解决什么问题、当前代价、预期改善、如何判断成功”，写入 PRD §1 的素材。已有明确答案直接复用，不单设金额门槛，也不要求用户再次确认价值。

收益数字必须有来源；用户提供但未实测的数字保留“假设值、依据、验证方法”。缺少量化证据时写清已知的可观察结果和证据缺口，不反推数字。只有缺口会改变方向、范围或风险接受时，才把具体问题交用户拍板；其余作为非阻塞假设继续。

---

## 阶段 3 · 定向查证（按需）

1. 从 `open_questions`、场景锚点或方案中的具体疑点确定要回答的问题，先复用当前项目资料和已有证据。
2. 只在外部事实影响当前方案时读取对应 `playbooks/{saas|mobile-app|ecommerce|generic}.md`，按问题选择官网、竞品、评论、行业数据或技术资料。品类通常由已知需求判断；不为挑 playbook 单独提问。
3. 调研数量和深度以能否支持当前判断为准，不固定竞品数量，不要求每个项目完成竞品全景、差评和 benchmark。没有此类问题时直接继续，不生成空报告。
4. 通过可用的联网搜索工具真实查证，记录来源 URL、适用范围和结论；产物按内容写入 `evidence/competitors.md` 或 `evidence/benchmark.md`。找不到的标“未找到公开资料”，不编造。
5. 已有证据足以支撑方案时立即继续。证据冲突或缺口只阻塞依赖它的判断；用户需要接受风险或改变业务选择时，说明依据、推荐和代价后请其拍板，不询问“调研是否足够”这种流程问题。

## 阶段 4 · 方案 V0 + 问题驱动评审

### 4.1 出 V0 方案概要

- 基于场景锚点、假设清单与实际相关查证材料（如有），写出 `{项目名}/proposal-v0.md` 后立即给用户查看入口，说明“初版，待完善”，继续处理实际问题；展示不新增确认等待，也不代表用户已批准方案
- 包含：解决思路 / 交付物清单 / 功能清单（带优先级）/ 角色与操作面 / 方案前置能力 / 外部能力配置责任 / 关键决策点

### 4.2 检查方案，按问题派评审

V0 已提供给用户查看后，由 Controller 对照已确认输入处理工程可行性、用户流程、运营责任和价值假设中的实际问题。已有证据能直接判断的问题自行处理；存在跨专业疑点、关键依赖不确定性或重大风险时，派对应 Reviewer 独立复核：

- `agents/reviewer-tech.md` — 工程视角
- `agents/reviewer-design.md` — 设计视角
- `agents/reviewer-business.md` — 商业视角（运营/资源/变现）
- `agents/reviewer-strategy.md` — 战略视角（对齐/底层假设）

每个任务给出场景锚点、当前方案、已确认边界、需要判断的具体问题与相关证据。只报告有位置、依据和后果的问题，按 🔴致命 / 🟠严重 / 🟡一般 / 🟢建议 分级；未发现问题可以直接通过，不要求凑问题或新角度。

### 4.3 合并意见，修订受影响部分

对每条问题作 **接受**（修订）/ **驳回**（给依据）/ **待决**（需要企业家拍板）的处理。只修改受影响内容；若没有需修订项，V0 可直接作为 V1 待确认。

涉及新业务、范围、价值取舍或尚未确认的产品决定，先交用户拍板；不能靠作者互相讨论把未知补成既定需求。

### 4.4 有具体疑点才复查

只有修订可能引入新冲突、关键问题尚未关闭或评审意见有证据分歧时，才把具体问题和变更交相关角色复查。已关闭问题没有新证据不重开，不要求全员再评一遍。未决事项需要外部证据或用户决定时，说明所缺信息并等待，不用重复互审代替查证或拍板。

**收敛条件**：方案已覆盖已确认范围；发现的问题已有修复、驳回依据或明确的待用户决定项；没有需继续内部调查的阻塞。满足后立即展示 V1 及真实待决项。已确认的内容直接继承，新增或改变的业务选择才交用户确认；内部评审不能替代用户决定。

### 4.5 输出 V1 方案 + 写入 debate-log.md

- 记录实际检查的问题、依据、处理和待决项；没有专业复核时如实记录 Controller 的检查结论，不伪造角色发言或轮次。
- 展示收敛后的 V1，标明沿用的已确认决定与尚未决定项。方向、方案已获明确确认且未改变时，记录原确认来源并直接继续，不再问一次“接受 V1 吗”。
- 新增或改变的产品决定用 AskUserQuestion 拍板后更新受影响部分。写入 `state.json.stage_confirmations.stage4_5_v1`，只对新增疑点补查，不重跑未变化的评审。

### 4.6 首版边界与完成定义

进入 PRD 终稿前，确保 `proposal-v1.md` 的「MVP 划分（已与企业家确认）」记清当前阶段功能、后续功能、完整多端/渠道/接口范围、方案前置能力和可观察完成定义。这里的“已确认”可以来自阶段 1 的整体方案或既有明确指令，不要求再跑一轮逐功能确认。

- 边界已明确：原样继承并标明确认来源；不得由 author 擅自删减、后置或发明范围。
- 仍有实际范围取舍：先给推荐、依据和代价；同一依赖前沿可一起确认，互相依赖的选择分轮处理。
- 用户未要求分期且已确认本次全部交付时，按完整范围定义本次完成；不能为套用 MVP 模板自动削减。

确认来源与完成定义写入方案，更新 `state.json.stage_confirmations.stage4_6_mvp`。只对缺失的业务决定提问，不因历史字段或标题缺失重复询问已有明确答案。
