# PPT 大纲规范

仅在用户有汇报需要或明确请求 PPT、执行阶段 6.1 时读取；PPT 不阻塞核心 PRD 或 Design/TDD。将 `output/PRD详细版.md` 转为 `output/ppt.md`，供业务、产品和技术负责人直接阅读：问题是什么、准备怎么解决、分几步走。本文件是八段结构、页数和内容来源的唯一事实源。

## 内容要求

- 全部结论来自 PRD，不补问、不重做技术决策、不臆造模块、指标或流程。关键结论和交付边界必须保留；没有事实依据的数据不能包装成结论，必要示例明确标为“示例/参考/区间/可配置项”。
- 前两页让读者理解问题和代价；产品设计说明怎么解决；路线图说明先后顺序和本次 MVP。
- 一页一个核心判断，标题与正文一致；其余为必要证据、数据或图表。同一结论跨页不重复铺写，后续呼应只用关键词。
- 每页按 16:9 横向画布组织，文字区域不超过内容区一半；叙述文字不超过 500 字（表格数据不计，HTML 再压到 300 字）。能用图表、表格、清单表达就不铺长段；不凑满版面或用空话替代信息。

# 工作流程：8 段固定结构

| 段 | 内容 | 唯一输入 |
| :--- | :--- | :--- |
| 1 · 首页 | 产品名 + 一句话定位 | PRD 标题 / §1 |
| 2 · 执行摘要 | 一页讲清“我们到底做了什么” | PRD 一句话方向 + 核心价值 |
| 3 · 核心痛点场景 | 具体用户在具体场景的真实困境 | PRD 痛点 / 用户场景 |
| 4 · 预期改善与成功标准 | 已有收益依据、可观察结果与证据缺口 | PRD §1 收益 / 成功度量 |
| 5 · 产品设计（≤3 页） | 核心设计、能力和解决方法 | PRD 功能需求 / 核心闭环 |
| 6 · 技术方案（2-3 页） | 数据、架构、风险与技术债 | PRD 技术章节 |
| 7 · 步骤阶段 | 完整阶段路线图 | PRD §0 阶段路线图 |
| 8 · 本次训练营要做的阶段 | 本次 MVP 与完成定义 | PRD §0 MVP |


产品设计最多 3 页，技术方案 2–3 页，总页数通常 10-12 页；信息少用短页，不为凑页数重复。承担相同判断的页面可以合并，但八段的关键结论都要覆盖。

## 按语义选版式

- `L0-Minimal`：一个结论与极简证据，适合内容较少的页。
- `L1-Split`：图文分栏；`L2-Process`：流程、演进或时间线。
- `L3-Architecture`：系统组成和模块关系；`L4-Grid`：确有必要的并列能力。
- `L5-Data`：关键数据或仪表盘；`L6-Compare`：现状与方案比较；`L7-Table`：参数、清单和规格。

按信息关系选用，不强制分栏或所有页面统一版式。

## 每页格式

```markdown
## P[序号]: [来自实际内容的结论标题]
> L1-Split

[可直接阅读的成稿，按所选版式用短句、表格或图示组织]
```

版式代码只作制作元数据，不显示到 HTML 页面。需要补充图形制作说明时，用 HTML 注释与可见文案区分，HTML 生成时只按其绘图，不把指令作为页面正文。

## 业务表达与输出边界

- 正文优先说明“什么能力、带来什么价值、有什么条件或限制”。底层名词如 Kafka、JWT、IndexedDB 只有在客户明确要求的采购/合规条款中直接展示；必要实现细节放章节末的技术说明，控制在 1–2 行。
- 标题和文案直接呈现痛点、目标、方案、指标、交付边界、风险和阶段，不写“本页策略、设计师指令、输出模板、接下来、我们将”等制作话术。
- 页面连续编号为 `P1, P2…`，输出纯 Markdown；不带 `contentReference`、`oaicite`、`index=` 等内部引用占位符或生成过程说明。
