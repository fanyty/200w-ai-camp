# Solution → PRD → Design → TDD 连续执行

默认链路为 Solution → PRD → Design → TDD；每个 Master 只负责本阶段产物，Controller 负责按输入门禁调度。“开始产品落地”“开始 PRD”和“继续，进入 PRD”都先检查有效前置，不能跳过 Solution。前置完整有效时直接复用并恢复实际进度，不重做有效产物；缺失前置不能用下游材料追认或补造。用户明确暂停、终止或只修改当前阶段时尊重其要求，但不因此放行缺失输入。Git 独立，不自动启动。

## Solution 前置与交接

Feature 每次进入或恢复 PRD，都核查同项目真实、已确认且适用于本次范围的 `output/解题方案书.md`，结合 `solution/state.json` 与确认来源验证停止条件已满足。无论是否曾启动 Solution，缺失、未完成、未确认或过时都先说明具体缺口，再从当前环境已发现的 Skill 清单定位 `solution-master`，实际读取并执行其 `SKILL.md` 补齐；不开始 PRD 访谈、方案或写作。Skill 缺失时报告具体名称和下文的全套安装入口，不凭名称模拟，也不由 PRD 代写方案书。已有有效回答与证据按 Solution 恢复规则沿用；其阶段、追问、停止条件和状态记录均按原文执行。

其 `AskUserQuestion` 在接入层对应当前平台的原生结构化选择工具，保留选项与自定义回答；事实题按 Solution 的开放回答规则执行。没有可用选择工具时如实说明能力缺口，不伪称已经弹出选择框，也不把事实题强行改成选择题。

Solution 停止条件满足并产出同项目的 `output/解题方案书.md` 后，交付实际路径、修改入口和接续句“继续，进入 PRD”。这句回复承接 PRD → Design → TDD；已有明确连续执行要求和有效方案确认时直接沿用，不重复索要交接授权。PRD 阶段 0 按 `SKILL.md` 的“承接解题方案书”读取并转化上游内容，不能把方案书作为整条产品链路的终点。未决业务问题仍按原提问规则解决，“别问了”“你来定”不能作为闸门已通过的证据。

`solution/state.json` 由 Solution 原样维护，PRD 接管后使用项目根目录的既有 `state.json`；两者不合并、不互相覆盖。仅有 PRD、代码、设计、TDD 或状态中的完成标记，不能证明 Solution 已完成，不能用其倒填方案或伪造确认。只有真实 Solution 输入及其有效确认核实后，才复用当前 PRD/Design/TDD 产物；前置不完整时先切换所属 Master 补齐，原有有效内容保留。

## 一次进入，共用输入

以下为进入 PRD 后的调度；Solution 尚未交接时不启动此段。

1. 调度 Design、TDD 时，分别从当前环境已发现的 Skill 清单取得真实位置，实际读取对应 `SKILL.md` 并切换职责；按各自输入门禁和产物规范执行。不要假设它们位于用户项目或与 PRD 相邻。需要的 Skill 缺失时准确报告具体名称，给出全套安装入口 `https://200w.liurun.vip/skill/product.md`；只继续当前职责内的可做工作，不代写缺失 Master 的产物、不伪称已执行，不写生产代码。
2. 沿用用户明确指定的项目和 Solution 已使用的同一个 `{项目名}/output/`。只有多个项目且意图无法判断时才让用户选择。将 PRD 的 `state.json.delivery_target` 设为 `tdd`；PRD/Design/TDD 共用这份状态、问题清单，不另建任务图，也不覆盖 Solution 状态。
3. 先读用户已有材料和当前有效产物。已经确认的场景、目标、角色、本次范围、设备、渠道、风格、外部能力和决定直接继承，并保留依据。信息确实变了或相互冲突才重问受影响项。用户已讲清想法时，不重新要求自由讲一遍。

Feature 的本次范围继承 `requirements.md` 的 `Metadata.scope`；只有旧契约未声明该字段时才兼容为 `MVP`，显式空值不算已确认范围。后续阶段或多阶段请求按已确认 scope 推进，不改写 REQ 原有的 `Stage`，不缩成 MVP；同一实际页面的阶段归属与当前产物沿用 Design 的稳定页面身份规则。

## 按输入门禁接续

进入 PRD 后，PRD、Design、TDD 分别负责各自产物，本节只负责调度，不赋予 Controller 跨阶段代写权限。已确认内容直接继承，必要的本阶段问题按相应 Skill 继续澄清；既不重问已确认事项，也不因连续执行跳过输入和确认。

以下依赖表仅适用于 Feature；其中 UI 动作沿用 Design 的适用规则，无 UI 影响时只推进非视觉设计与技术方案：

| 已有条件 | 立即推进 | 还不能做 |
| :--- | :--- | :--- |
| Solution 方案与停止条件已核实，关键决定已有有效确认 | PRD 继承方案并补产品层缺口，生成核心 PRD、requirements 与分析 | 未确认角色、渠道或范围不能写成已决定；PRD 不代写设计 |
| PRD 核心三份齐备、范围已确认、P0/P1 清零且必要校验通过 | 读取 Design Skill，交付同版输入，按其规范形成蓝图 | PRD 未收口时不以草稿启动 Design 产物 |
| Design 已取得有效上游，可见蓝图待生成范围已获确认 | 由 Design 生成本期完整设计、适用 MD/HTML、技术方案与追溯 | 不用未完成设计或伪造 ID、路径、HTML 基线启动 TDD |
| 本次 scope 的真实设计及追溯齐全，来源和范围一致 | 读取 TDD Skill，在同一目录生成完整验收契约并执行自身校验 | 有来源冲突、遗漏或未决关键结果时不能声称契约完成；不开始生产实现 |

只把当前前沿中互不依赖、需要用户决定的问题合并提问。先给用户可理解的推荐和取舍；未知事实先自行查证。用户回答一部分就更新已知条件，推进本阶段可做部分。产品方案/本次范围与可见设计蓝图是不同决定，按输入门禁依次形成与确认；已有有效确认直接沿用，没有展示的设计不能借产品确认视为批准。

业务主线始终落到“谁提供什么输入 → 系统如何处理 → 谁获得什么可用结果”。功能、页面与验收围绕这个闭环生成，不能只剩数据展示或通用后台。已确认的端、渠道、接口和本次 scope 的页面完整保留。

调研只解决会改变当前决定的具体未知。PRD-summary、PRD-dev 和方案 PPT 按用户用途生成，不阻塞设计或 TDD，也不以产物缺失为由重启已完成访谈。子 Agent 只承接可独立推进的任务，共享同一版来源；由 Controller 维护需求 ID 和 revision，避免各自产生一套编号。

**Bugfix**：沿用既有专用规格路径。`bugfix.md` 的 REPRO/CUR/EXP/UNCH/CON 与修复范围已明确且必要校验通过后，读取 Design Skill，由 Design 按复现、代码与日志证据定位根因，形成最小修复设计 `修复设计.md`、`设计追溯矩阵.md` 和 `change-impact.md`；真实修复设计、追溯及受影响产物齐备后，再读取 TDD Skill 生成契约并执行自身校验。无法复现或根因未证实时，继续调查，不把假设写成根因或放行下游。Bugfix 不要求 Feature PRD；无 UI 修复不要求页面清单或 MD/HTML，仅更新实际受影响的设计。

## 继续与交付

PRD 接管后，每阶段完成即调度满足输入条件的下一 Master，不要求用户再输入“开始 Design”“开始 TDD”。缺前置时说明具体缺口，并实际读取所属 Master 的 Skill、切换职责补齐；不能由 Controller 代写上游，也不让用户重新讲已有背景。只读调查与当前职责内不依赖缺项的准备可以继续，但不能据此启动受阻阶段的产物。

每阶段交付都给出实际产物路径、修改入口、下一阶段和具体接续句：Solution →“继续，进入 PRD”，PRD →“继续，进入 Design”，Design →“继续，进入 TDD”；TDD 按下文给出完整 Goal 的使用方法。已在连续执行时直接推进，接续句只用于中断后恢复，不作为新的阶段审批。

中断时复用 `state.json.next_action` 记录正在等待的决定或下一项工作及实际产物位置。恢复先核查本工作类型的有效前置，再读 `delivery_target`、产物和未决项；Feature 的 Solution 缺失或过时不能因 PRD 已完成而豁免。前置有效后从 Design/TDD 的实际缺口继续，不能因 PRD 结束把整条链路标为完成。来源变更时调度对应 Master 只更新受影响产物，未变部分沿用。

最终按已有 `work_type` 交付同一 `output/` 的实际产物：

- `feature`：真实已确认且仍有效的 `解题方案书.md`、实际承接其结论的核心 PRD、需求契约与分析、完整本次 scope 的设计、设计追溯矩阵和 `tests/TDD验收契约.md`；前置缺失时不得宣称整链完成，也不得倒填方案书。
- `bugfix`：`bugfix.md`、`修复设计.md`、`设计追溯矩阵.md`、`change-impact.md`、实际受影响的设计产物和 `tests/TDD验收契约.md`。

给出查看入口及尚未解决的实际问题。这里完成的是开发输入，不能说产品已开发、测试已通过或已上线。只有 TDD 验收契约完整且校验通过后，才按 `tdd-master` 阶段 3 的交付提示，给出 `https://200w.liurun.vip/skill/goal.html`，说明复制完整命令、保留 `/goal`，并在同一项目的新 Code 对话中执行；不得在安装、解题或 PRD/Design 阶段提前引导执行。用户已授权继续开发时沿用授权，否则交付到本入口约定的验收契约并给出这一步使用指引。
