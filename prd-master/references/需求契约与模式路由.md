## 1. 流程路由

普通“启动 PRD / 开始新项目 / 新建 PRD”按 Feature 路由，必须先核实同项目真实、已确认且仍有效的 Solution 方案及其状态/来源；缺失、未完成或过时先读取 Solution Skill 并切换补齐，不能因用户点名 PRD 或已有代码而跳过。门禁通过后使用 `work_type=feature`，不得询问 Feature / Bugfix 二选一；只有用户明确提出“做 bugfix 规格”“整理复杂缺陷”或等价意图时，才使用 `work_type=bugfix` 并读取既有 `Bugfix专用链路.md`。Feature 自动按证据路由，不让用户选择流程模式：

| mode | 适用证据 | 核心要求 | 额外动作 | 用户拍板 |
| :--- | :--- | :--- | :--- | :--- |
| `standard` | 默认；包括成熟、通用、低风险的简单需求 | 完整 PRD、requirements、正确性分析、必要校验；摘要按用户用途从核心提炼 | 按真实未知定向调研，按具体疑点评审；PPT 仅在有汇报需要或明确请求时生成 | 只确认实际未决的方向、行为、范围、成功标准和重大取舍；继承已有明确决定 |
| `tech-constrained` | 既有架构、严格延迟/吞吐/合规或迁移约束真实决定范围 | 与 `standard` 相同，完整保留已确认范围 | 在固化方案前补技术可行性预检 | 只有可行性证据要求改变业务选择时再请用户拍板 |

普通 Feature 直接写入 `workflow_mode=standard`。只有查到硬技术约束证据时才写入 `tech-constrained`，并输出 `evidence/technical-feasibility.md`：硬约束、现有系统证据、候选方案、不可行项和受影响范围。没有代码/文档证据时只能标假设，不能宣称可行。范围调整必须由用户确认，不能以加速为由削减多端、渠道或接口。

阶段编号沿用；定向调研和 PPT 按实际需要执行，不要求固定调研数量、旧价值金额确认或额外阶段审批。恢复规则以 `docs/STATE-MANAGEMENT.md` 为准。默认按 `references/连续执行.md` 的输入门禁接续 PRD → Design → TDD，现有 `state.json.delivery_target` 默认为 `tdd`；有效上游可以复用，缺失前置不能用下游产物豁免。Controller 调度时实际读取对应 Skill，不代写其他阶段产物或生产代码。用户明确暂停、终止或只修改当前阶段时按其指示保存或处理，但不放行缺失输入。

## 2. 稳定 ID

| 对象 | 格式 | 示例 |
| :--- | :--- | :--- |
| 功能 | `Fnn` | `F03` |
| 用户故事 | `US-Fnn-nn` | `US-F03-01` |
| 行为需求 | `REQ-Fnn-nn` | `REQ-F03-02` |
| 验收条件 | `AC-Fnn-nn` | `AC-F03-04` |
| 非功能需求 | `NFR-nnn` | `NFR-006` |
| 假设 | `A-nnn` | `A-014` |

规则：

1. 在场景锚点首次形成需求清单时分配；跨 PRD、requirements、设计、测试、任务原样传递。
2. 发布后永不重编号、复用或因排序改变；删除项保留并标 `retired`，替代项写 `supersedes`。
3. 一个 AC 只验证一个可观察结果，并且必须有 `Parent: REQ-*`。
4. 文案变化不换 ID；行为语义变化保留 ID 但递增 `revision`，拆分后旧 ID retired、新增 ID。
5. PRD 与 requirements ID/语义不一致时暂停受影响下游项，先修单一事实源；不得让 design-master 猜。

### 2.1 关键决策与需求契约的边界

产品/架构决定只有通过 PRD 的三条件关键决策闸门，才写入 `PRD详细版.md` 一张简表并索引到 `state.json.key_decisions_made`；不创建独立 ADR/DR。若决定改变系统行为、阈值、兼容性或约束，必须同时落实为对应 `REQ/AC/NFR`，下游仍以这些稳定需求 ID 为事实源。

design-master 的 `DEC-nnn` 只用于没有直接 source ID 的设计层衍生决定，并写明必要性；不得拿 `DEC-nnn` 复制或替代 PRD 中的产品/架构决策记录。

## 3. EARS 契约

使用 `templates/requirements.md`。每个 AC 至少包含：

```text
WHEN <可观察的事件或条件>
THE SYSTEM SHALL <唯一、可验证的结果>
```

需要时使用 `WHILE <状态>`、`WHERE <可选能力>`、`IF <异常条件>` 补充前置语境，但最终必须有 `THE SYSTEM SHALL`。禁止“快速、友好、足够、大文件”等未量化词；把阈值、单位、时间窗、角色、数据范围写清。

`Metadata` 必须填写 `work_type / workflow_mode / revision / source_prd / status`；`revision` 为正整数。每个 active REQ 必须保留 `Stage / Revision / Status`，每个 AC 的条件和结果都须有实际内容，不能交付未填写模板。`Metadata.scope` 记录本次已确认交付阶段，用逗号分隔，例如 `MVP, 阶段2`；缺少该字段的旧契约按 MVP 解释，显式空值无效。`MVP` 与 `阶段1（MVP）` 是同一阶段，阶段数字按完整值匹配；“试点期”“全量交付”等已确认名称按完整名称匹配，不强制改成编号。每个 scope 名称须对应 active REQ 的 Stage。启动后续阶段时更新 scope，保留各条 REQ 原有 Stage；Design 蓝图和 TDD 沿用这份范围。

每个 US 必须有 `Role`，并使用 PRD 角色矩阵中的稳定名称或已列别名。`External capability configuration` 表也必须保留：没有外部能力时只写 `none`；否则逐项写凭据归属、配置角色、配置入口、作用域、生命周期、所属阶段和对应需求，配置角色同样使用稳定角色名。`Surface` 只使用 `deployment-secret / onboarding / settings / admin / none`，`Scope` 只使用 `system / tenant / user / project / none`。`onboarding / settings / admin` 属于产品行为，必须关联至少一个真实 REQ；`deployment-secret` 只有在 PRD 已明确由内部技术人员统一部署时才可选，不能替代客户或用户自助配置。

`Capability prerequisites` 表同样必须保留：没有方案前置能力时只写 `none`；否则逐项记录状态、负责人、可核验证据或承诺截止时间、不可用时的替代方案、所属阶段和对应需求。本次 scope 内已确认依赖的 `Status` 只使用 `ready / committed`：`ready` 必须给可核验证据，`committed` 必须给负责人和截止时间；当前不可用且没有可信承诺的能力不能伪装成已解决，应按现有授权改选替代方案，确实需要改变已确认范围时再请用户决定。后续阶段可如实保留 `planned / unknown`，进入该阶段时再核实。关联本期 REQ 的能力始终按本期依赖判断，不能靠把表内 Stage 写成后续阶段绕过检查。

认证通道、第三方平台登录、移动应用分发账号/签名、支付、推送、硬件或行业资质等确实被本次方案采用时，才需要落实对应前置能力。正文中的能力关键词只提示复核；否定句、已废弃项、对照方案和未来规划不证明本期依赖，不据此强制新增配置或提问。

PRD 负责解释价值、场景与取舍；`requirements.md` 只保存下游必须实现和验证的行为，不复制研究过程。

## 4. 正确性分析

生成 `requirements-analysis.md`，按完整需求集合检查：

1. 逻辑不一致：两条单独合理、合在一起不可满足。
2. 含糊量词：会让两个实现者得到不同结果。
3. 约束冲突：功能、性能、安全、合规、成本无法同时满足。
4. 未声明假设：未定义角色、实体、状态、时间或外部系统。
5. 缺失路径：失败、边界、并发、重试、幂等、权限与恢复。
6. 不可验证指标：没有阈值、采样方式或时间窗。

固定结尾：

```text
P0 unresolved: 0
P1 unresolved: 0
```

每条发现列出涉及 ID、失败模式、建议修复和最终决议。PRD 核心三份齐备、P0/P1 清零且必要校验通过后，才按 `references/连续执行.md` 交给 Design；未达条件时只继续 PRD 内无依赖的写作与只读查证，不提前生成设计蓝图或 TDD 产物。

使用模板的 `Scope / Findings / Summary` 三节；Scope 的 revision 必须对应当前需求契约。Findings 无发现时保留空表，已关闭项填写具体 Resolution；Summary 只保留一份当前计数，必须与 Findings 中实际未解决的 P0/P1 一致，历史零值不能覆盖当前问题。

## 5. 增量同步

修改需求时输出影响集合：变更 ID、revision、直接依赖、下游需标 `stale` 的设计/测试/任务。只重生受影响项；未受影响 ID 与状态保持不变。已完成任务映射的上游 revision 未变，且已有验证证据仍适用时，保留 completed 并复用证据；只有相关改动、失败或具体疑点才定向重跑受影响检查，不要求每次恢复都补一轮 fresh regression。
