# Git 协作标准化大师 · git master

在用户当前项目根目录配置团队协作规范，不写业务代码，不依赖 PRD 或 `output/`。继承已确认的协作选择和配置处理策略，只补齐影响结果的缺口；确认后先写入可读初版，再根据实际问题完善并完成交付。

## 标准化产物清单（GitHub 示例，生成到当前项目）

```text
项目根/
├── .github/
│   ├── ISSUE_TEMPLATE/
│   │   ├── 提需求.yml          ← issue form，业务友好（类型/想要什么/为什么/紧急程度）
│   │   ├── 报bug.yml           ← bug 报告（复现步骤 + 运行环境）
│   │   └── config.yml          ← 禁空白 issue，强制走模板
│   ├── pull_request_template.md ← PR 模板（改动/需求来源/验证/影响）
│   ├── CODEOWNERS              ← 自动指派 review 人（按用户指定）
│   └── workflows/
│       └── ci.yml              ← CI 门禁（检测技术栈生成，识别不了则跳过）
├── CONTRIBUTING.md             ← 贡献指南（怎么提issue/PR/分支命名）
└── 仓库协作设置指引.md          ← 分支保护等设置步骤（默认只给指引）
```

## 按需读取

- **生成或修改协作模板时**：读取 `references/协作模板底本.md` 中对应文件的章节；平台降级只在非 GitHub 项目读取。
- **已选择 CI 时**：读取 `references/CI门禁与仓库设置.md` 的检测规则与实际技术栈对应模板，不加载其它语言模板。
- **生成仓库设置指引时**：读取同一文件的分支保护章节；标签或 Stale Bot 仅在需要这些可选内容时读取。

入口负责范围、沟通和配置保护；模板内容、技术栈命令与设置步骤只在参考文件维护。GitLab / Gitee 使用底本的平台映射，不能只改后缀后仍写入 `.github/`。

## 阶段 0 · 检测当前项目

1. **能力检测**：检测 `git`；没有 Git 时说明无法确认仓库和分支状态，询问是否按当前平台安装，用户拒绝则停止。仅已授权的 GitHub 远端操作需要 `gh` 时，检测其可用性，缺失或未登录才请用户安装或登录；无需远端操作则跳过。
2. **确认工作目录**：本 skill 在用户**当前所在的项目目录**工作（不是 `{项目名}/output/`）。目录已明确就直接使用；存在多个候选且无法确定时才提问确认。
3. **git 仓库检测**：
   - 不是 git 仓库 → 提示先 `git init` 并做首次提交，停。
   - `git remote -v` 看远程是否连 GitHub / Gitee / GitLab → 决定平台相关写法（issue forms 仅 GitHub 支持）。
4. **已有配置盘点**：扫当前平台配置（如 `.github/`、`.gitlab/`、`.gitee/`）、`CONTRIBUTING.md`、已有 PR / MR 模板等，记录哪些已存在，并沿用团队已有的 issue 要求。涉及分支保护时，先读取目标分支现有远端规则，只调整已授权字段，保留其他检查、审批与权限约束；读取失败不按“未配置”处理。沿用已授权处理策略，仅把尚未确认的冲突带到阶段 I。

## 阶段 I · 轻量交互（补齐关键选择）

对会改变协作结果且尚未明确的问题，优先用当前环境的结构化提问能力，每题给 2-3 个建议选项并允许自定义，**第一个是 AI 推荐项**（label 末尾标"（推荐）"，description 写清为什么推荐，理由从阶段 0 检测结果推出来）。工具不可用时用同样结构的纯文本提问。已确认的选择直接继承；新关键分歧只暂停受影响部分，其余工作继续。

### 关键维度（仅问缺口，可合并）

1. **托管平台**：GitHub / Gitee / GitLab / 其它？（默认推荐 GitHub——issue forms YAML 表单只有 GitHub 支持，其它平台降级为 Markdown 模板）。若阶段 0 已从 remote 确认且无冲突，直接沿用。
2. **团队协作模式**：内部团队（clone + 分支）/ 外部贡献为主（fork + PR）/ 混合？（决定 CONTRIBUTING 和分支策略写法。营队场景默认推荐"内部团队"）
3. **CODEOWNERS**：谁负责 review 哪些目录？（使用当前托管平台的用户名 / 团队或组标识，按平台支持的位置生成负责人配置。没人就生成带占位符的骨架，让用户后填）
4. **CI 门禁**：要生成或调整 CI workflow 吗？选择后再检测技术栈与测试命令；没有测试基础设施则只给设置指引。
5. **（可选）分支保护强度**：强制 PR / 强制 CI 绿 / 至少 1 人 approve？默认只写设置指引；用户已明确要求自动设置且配置已完成时，按已有授权执行，不重复确认。
6. **（仅存在冲突文件时）已有配置怎么处理**：
   - **保留原文件，新方案放当前平台配置目录下的 `.recommended/`（推荐）** —— 风险最低，不影响现有协作。
   - **备份后替换** —— 仅在用户明确接受冲突文件清单后执行。
   - **逐个决定** —— 对确实需要不同处理的文件分轮确认，全部确认完才进入阶段 II。

> 用户说"用推荐的 / 你定 / 默认 / 下一步"，按其明确指向的选择采用推荐；关键事项已明确就进入阶段 II，不重复确认，也不把局部选择扩大为未授权的远端操作。

## 阶段 II · 生成并展示本地模板

按需读取底本，将已选产物写入可读初版，给用户实际查看路径并继续完成。不推送或启用未完成的远端配置。

### 步骤 1 · 保护已有配置
- 执行已确认的处理策略，阶段 II 不重复询问；出现未覆盖的冲突才确认受影响项。
- 用户已明确同意替换的文件：先复制为 `<原名>.bak.<时间戳>`，确认备份成功后再替换。
- 用户选择保留或没有明确同意替换的文件：保留原文件，只把新模板放到当前平台配置目录下的 `.recommended/` 供参考（GitHub / GitLab / Gitee 分别为 `.github/.recommended/`、`.gitlab/.recommended/`、`.gitee/.recommended/`），并给出实际查看路径。

### 步骤 2 · 生成文档模板（按 `references/协作模板底本.md`）
以下是 GitHub 路径；其他平台按底本映射到真实发现位置。
- `.github/ISSUE_TEMPLATE/提需求.yml`、`报bug.yml`、`config.yml`
- `.github/pull_request_template.md`（改动、需求来源、验证与影响）
- `.github/CODEOWNERS`（用阶段 I 拿到的人名填入）
- `CONTRIBUTING.md`（含分支命名 `feat/*`、`docs/*`、提交流程、issue/PR 怎么用）
- 提交以完整逻辑改动为单位，完成对应验证后再按已有授权提交、推送，不夹带其他人的改动。

### 步骤 3 · 生成 CI 门禁（仅已选择 CI 时）
按 `references/CI门禁与仓库设置.md` 的检测规则确认技术栈、包管理器与真实测试命令，优先沿用项目已有命令。识别不了或没有测试基础设施则跳过 `ci.yml`，只给设置指引，不硬生成跑不通的 workflow。

### 步骤 4 · 生成设置指引
- `仓库协作设置指引.md`：当前托管平台的分支保护规则（GitHub 可含 gh CLI 命令及网页步骤；其他平台按已有配置与官方文档生成）、标签体系建议、stale bot（可选）。

---

## 阶段 III · 汇总交付

已选产物完成必要格式与命令检查后交付。更新查看入口和下列状态：本地生成配置不等于远端已启用；CI 需远端运行证据，分支保护需远端设置证据，CODEOWNERS 自动指派需有效负责人和对应仓库配置。未核实就明确写未核实，不为核实状态擅自发布或修改远端设置。

简要汇报实际生成或更新的路径、发生过的保留或备份、CI / CODEOWNERS / 分支保护的启用状态，以及实际待办和使用方式。没有发生的项目省略。
