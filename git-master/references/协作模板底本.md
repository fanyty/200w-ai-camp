# 协作模板底本

> 本文件是 git-master 阶段 II 的协作模板底本；仅在生成或修改对应文件时读取相应章节。CI 与仓库设置另见 `references/CI门禁与仓库设置.md`。
> 执行时按底本生成到对应路径，把 `{{占位符}}` 替换为阶段 I 已确认的值或实际检测状态；GitHub 是下方示例平台，生成到其他平台时同步替换平台入口、PR / MR 名称、默认分支和负责人标识；不得把“建议启用”写成“已经生效”。平台为 Gitee/GitLab 时，issue 表单降级为 Markdown 模板（见文末）。

## 文件 1 · `.github/ISSUE_TEMPLATE/提需求.yml`

业务人员提需求 / 改动用的 issue form（仅 GitHub 支持 YAML 表单）。

```yaml
name: 提需求或改动
description: 业务人员用这个模板提需求、改动或报 Bug
title: "[需求]: "
labels: ["needs-triage"]
body:
  - type: markdown
    attributes:
      value: |
        感谢提需求！描述你想要的结果即可，不用写代码。
        填写前可以先看看是否已有类似 issue。
  - type: dropdown
    id: type
    attributes:
      label: 这是什么类型
      options:
        - 新功能
        - 改进现有的
        - 修 Bug
    validations:
      required: true
  - type: textarea
    id: what
    attributes:
      label: 想要什么效果
      description: 描述你想要的结果，无需技术细节
      placeholder: "比如：把首页登录按钮文案从『登录』改成『立即开始』"
    validations:
      required: true
  - type: textarea
    id: why
    attributes:
      label: 为什么要改（可选）
      description: 说一下背景，帮助开发理解优先级
      placeholder: "比如：用户反馈『登录』两字不够吸引点击"
  - type: dropdown
    id: urgency
    attributes:
      label: 紧急程度
      options:
        - 不急
        - 这周要
        - 很急
    validations:
      required: true
```

## 文件 2 · `.github/ISSUE_TEMPLATE/报bug.yml`

Bug 报告表单，保留复现步骤和运行环境。

```yaml
name: 报 Bug
description: 报告一个出错的问题
title: "[Bug]: "
labels: ["bug", "needs-triage"]
body:
  - type: markdown
    attributes:
      value: |
        感谢报 Bug！请尽量填全，信息越全修得越快。
  - type: textarea
    id: what-happened
    attributes:
      label: 出了什么问题
      description: 一句话描述现象
      placeholder: "比如：点登录按钮后页面白屏"
    validations:
      required: true
  - type: textarea
    id: reproduce
    attributes:
      label: 怎么复现（关键）
      description: 按步骤写，让别人能照着重现
      placeholder: |
        1. 打开首页
        2. 输入账号密码
        3. 点登录
        4. 页面白屏
    validations:
      required: true
  - type: textarea
    id: expected
    attributes:
      label: 本来应该怎样
      description: 你期望的正确结果
      placeholder: "比如：登录后跳到首页"
    validations:
      required: true
  - type: textarea
    id: environment
    attributes:
      label: 运行环境
      description: 浏览器 / 系统 / 版本（尽量写全）
      placeholder: "比如：Chrome 120 / macOS 14 / App 1.2.3"
      render: shell
    validations:
      required: true
  - type: textarea
    id: logs
    attributes:
      label: 报错信息 / 截图（可选）
      description: 把控制台报错或截图贴上来
      render: shell
  - type: dropdown
    id: severity
    attributes:
      label: 严重程度
      options:
        - 小问题（不影响使用）
        - 中等（影响部分功能）
        - 严重（用不了）
    validations:
      required: true
```

## 文件 3 · `.github/ISSUE_TEMPLATE/config.yml`

控制 issue 模板选择器。**禁空白 issue**，强制走模板（有写权限的人仍可提空白，普通贡献者只能选模板）。

```yaml
blank_issues_enabled: false
contact_links:
  - name: 💬 提问 / 讨论
    url: "{{DISCUSSIONS_URL_OR_REMOVE}}"
    about: 不确定是不是 Bug 或需求？先来这里讨论。
  - name: 📖 使用文档
    url: "{{DOCS_URL_OR_REMOVE}}"
    about: 先看文档，你的问题可能已经有答案。
```

> 执行说明：`{{DISCUSSIONS_URL_OR_REMOVE}}` / `{{DOCS_URL_OR_REMOVE}}`——替换为真实 URL（保留引号）；若仓库没开 Discussions 或没有文档站，**整条 contact_links 删掉**，只留 `blank_issues_enabled: false`。

## 文件 4 · `.github/pull_request_template.md`

PR 模板保留改动描述、需求来源、验证结果和必要影响说明，填写深度随改动而定。正文使用 Markdown，可复用到各平台；文件位置按文末的平台映射生成。

```markdown
## 改了什么 & 为什么
<!-- 一句话说清本次 PR 做了什么、为什么要改。reviewer 先看这句。 -->


## 需求来源
<!-- 有关联 issue 时填写链接或编号；本 PR 完整解决且需自动关闭时写 Closes #编号。没有强制 issue 要求时，可引用已有 PRD / 需求记录，或摘录对话中已确认的需求。 -->

## 类型
- [ ] 新功能
- [ ] 改进 / 优化
- [ ] 修 Bug
- [ ] 文档
- [ ] 重构（不改行为）

## 验证
<!-- 写实际执行的检查与结果；未验证的重要部分说明原因。按改动影响验证，无须凑齐测试类型。 -->

## 改动影响
- [ ] 这是不向后兼容的改动（已标注迁移方式）
- [ ] 我更新了相关文档

## 截图 / 录屏（可选）
<!-- 涉及界面改动时贴上来，方便 reviewer 判断。 -->

```

> 执行说明：GitHub 默认放 `.github/pull_request_template.md`（仓库根 / docs / .github 三处均可识别）；其他平台按文末映射，不能只复制正文到 GitHub 路径。

## 文件 5 · `.github/CODEOWNERS`

自动指派 review 人。格式：`<规则路径> @用户名 @团队名`。

```text
# CODEOWNERS —— 谁负责 review 哪些目录
# 格式：<文件/目录规则>  @GitHub用户名  @团队名
# 详见 https://docs.github.com/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners
#
# 用阶段 I 拿到的人名替换下面的占位符；没人负责就留骨架让用户后填。

# 默认负责人（所有没被更具体规则覆盖的改动）
*                              @{{OWNER_1}}

# 按目录指派（按需放开）
# /src/backend/                @{{BACKEND_OWNER}}
# /src/frontend/               @{{FRONTEND_OWNER}}
# /docs/                       @{{DOCS_OWNER}}
# /.github/                    @{{OWNER_1}}
```

> 执行说明：这是 GitHub 示例，`@{{OWNER_1}}` 等替换为阶段 I 确认的 GitHub 用户名或组织团队标识；GitLab 等平台使用其有效身份格式与配置位置。用户没给具体人 → 保留占位符并在汇报里提示"负责人待填"。

## 文件 6 · `CONTRIBUTING.md`

贡献指南。告诉所有人：怎么提 issue、怎么提 PR、分支怎么命名、营队链路（可选）。

```markdown
# 贡献指南

感谢参与！无论你是业务、开发还是 AI 助手，改这个项目前请先看这里。

## 一、说明改动需求

沿用团队已有的 issue 要求：要求先开 issue 的项目照常执行，已有 issue 直接引用。没有强制要求且需求已明确时，可直接提 PR，引用已有 PRD / 需求记录，或摘录对话中已确认的需求，无须重复建 issue。

需要新建 issue 时：

1. 去 **Issues → New issue**
2. 选模板：
   - 想要新功能 / 改东西 → **提需求或改动**
   - 出错了 → **报 Bug**
3. 填完提交。**不要提空白 issue。**

## 二、怎么改代码（开发 / AI Agent）

```
# 1. 拉代码 + 开分支（别在 main 上直接改！）
git pull
git checkout -b feat/<简短描述>      # 新功能用 feat/，改文档用 docs/，修 bug 用 fix/

# 2. 改代码（AI 在这个分支上干活）

# 3. 完成一个逻辑改动及对应验证后，按项目授权提交并推送
git add <本次改动文件>
git commit -m "<简体中文说明本次逻辑改动>"
git push origin feat/<简短描述>

# 4. 去 GitHub 提 Pull Request，说明需求来源
```

**分支命名约定**：
- `feat/*` 新功能
- `fix/*` 修 bug
- `docs/*` 改文档
- `refactor/*` 重构（不改行为）

提交以完整逻辑改动为单位，不按文件数拆分；相关验证完成后再提交，不夹带其他人的改动。

## 三、PR 合并条件

1. 已启用的 CI 检查全部通过；尚未配置 CI 时，提交对应的实际验证结果。
2. 按团队已确认的评审规则完成 review；有效 CODEOWNERS 已配置时由平台指派，否则按约定指定评审人。
3. PR 描述写清改了什么，引用关联 issue 或其他已有需求记录

**当前配置状态**：CI：{{CI_STATUS}}；CODEOWNERS：{{CODEOWNERS_STATUS}}；分支保护：{{BRANCH_PROTECTION_STATUS}}。仅有本地文件或设置指引时，写“待启用/待验证”；没有检测证据时写“未核实”。

## 四、铁律

- 通过分支和 PR 协作；分支保护是否已生效以上述实际配置状态为准，待启用项见设置指引。
- **main 上永远：文档 = 代码 = 测试**，三者一致。
- **改了行为就要同步文档**——别只改代码不改文档。
- AI Agent 只在分支上干活，绝不直接碰 main。

## 五、外部贡献者

没有仓库写权限？用 fork + PR：fork 本仓库 → 在你的 fork 改 → 从 fork 提 PR 回来。

---

> 这个项目用「200 万·AI 落地营」提示词套件开发。需求用 prd-master、设计用 design-master、测试用 tdd-master，协作规范由 git-master 配置。
```

> 状态字段按本次实际检测填写：CI 不存在或被跳过时写明原因；CODEOWNERS 没有有效负责人时写“待填”；分支保护只在取得远端设置证据后写已启用。不得因生成模板就宣称远端已经生效。

## 非 GitHub 平台：模板位置与格式

issue forms（YAML 表单）**只有 GitHub 支持**。Gitee / GitLab 用 Markdown 模板降级：

- **GitLab**：需求和 Bug 分别放 `.gitlab/issue_templates/提需求.md`、`.gitlab/issue_templates/报bug.md`；PR 正文放 `.gitlab/merge_request_templates/Default.md`，称为 merge request。CODEOWNERS 如需生成，使用 `.gitlab/CODEOWNERS` 并沿用 GitLab 负责人语法与项目权限。模板进入默认分支后才由平台发现。参见 [GitLab 模板文档](https://docs.gitlab.com/user/project/description_templates/) 和 [.gitlab 功能目录](https://docs.gitlab.com/development/features_inside_dot_gitlab/)。
- **Gitee**：中文 issue 模板使用 `.gitee/ISSUE_TEMPLATE.zh-CN.md`，在同一模板中给出需求 / Bug 两类填写入口；其他语言按对应语言后缀。PR 模板和评审人配置沿用仓库已生效的位置，缺失时查当前平台文档，不能套用 GitLab 或 GitHub 路径。参见 [Gitee 官方模板说明](https://gitee.com/opensource-guide/guide/participating/first-issue.html)。
- 内容用 Markdown 标题 + 占位符引导填写，例如：

```markdown
## 类型
新功能 / 改进 / 修 Bug（删掉不要的）

## 想要什么效果
<!-- 描述你想要的结果，无需技术细节 -->

## 为什么（可选）

## 紧急程度
不急 / 这周要 / 很急
```

- GitHub 的 `config.yml` 在 Gitee/GitLab **不生效**，跳过生成；CONTRIBUTING 写明平台实际模板入口，不声称禁空白 issue 已生效。

> 平台判定以阶段 0 的 `git remote -v` 为准；用户在阶段 I 确认。
