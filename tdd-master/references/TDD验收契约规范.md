# 规范 · TDD 验收契约

## 1. 唯一产物

默认只生成：

```text
output/tests/TDD验收契约.md
```

它同时承担完成定义、验收清单和完整 `/goal` 的整体验收完成条件。它不是完整开发提示词；不得把相同信息复制到测试索引、逐层 TDD、任务图、追溯矩阵或状态 JSON。

正式生成验收集合或写入契约前，必须按 TDD 主入口核验完整有效的 requirements/bugfix、设计追溯矩阵和适用页面的实际 MD/HTML。门槛未通过时只可只读调查和整理已有证据，不另建准备产物、不先写验收行；缺口按主入口切换实际所属 Master 修正，不能由 TDD 代写上游。通过后使用真实 Source/Design ID、revision 与产物组织契约，不得伪造 ID、路径或视觉 baseline。

## 2. 一条验收项的颗粒度

一条验收项必须满足：

1. 对应一个用户可观察结果，或一个独立的高影响业务约束。
2. 可以由一次连续操作或一组紧密相关断言验证。
3. 失败时能说明哪种产品能力没有交付。
4. 能引用真实 Source ID、Design ID 或上游产物。
5. 验证成本与风险相称，Coding Agent 能在完整开发循环中实际执行。

不按以下对象拆用例：

- 单个函数、组件、字段或断言。
- null、undefined、空字符串等业务后果相同的输入变体。
- 单元/组件/集成/E2E 等技术测试层。
- 为满足“每类至少一条”而虚构的场景。

只有不同分支会造成不同业务后果、需要不同实现或不同修复时才拆开。只引用必要的 Source/Design ID 与产物，不重述 PRD/Design；通过标准写出具体结果，不能只写“页面能打开”“请求成功”或“看起来正常”。

场景写明实际初始状态、待验动作和终点。初始数据可准备必要前置条件，但不得预先完成待验动作；例如分单可预置购物袋，支付可预置待付订单，但下单不能预置订单后只验展示。通过标准及期望值来自已确认规则或已知业务例子，不调用被测计算生成期望值，也不复制其实现充当独立答案；执行证据的结论限于实际验证的起点、动作和终点。

## 3. 来源覆盖

Feature：

- `scope` 沿用 requirements Metadata.scope；旧来源未写时为 MVP。多阶段以逗号分隔，`MVP`、`阶段1(MVP)`、`阶段1` 等价；其他编号阶段按编号精确匹配，兼容已有的阶段一至阶段十写法；“试点期”“全量交付”等实际阶段按完整名称匹配，不强制改名或编号。TDD 必须显式填写且与来源一致，每个选中阶段都必须匹配 active REQ；空值、未知阶段和零需求范围均失败。后续阶段已获确认时，按主入口回交规则由 PRD 更新来源 scope、Design 更新蓝图与设计，各自按实际 Skill 执行；重新通过入口检查后，TDD 仅更新本契约，不代写上游、不重写原 Stage，也不重复确认既定选择或新增状态。
- 覆盖当前 scope 的所有 active REQ。
- 覆盖这些 REQ 下所有 active P0/P1 AC。
- 覆盖所有明确声明且 active、适用于 scope 的 NFR（全局或 Applies-to 关联任一选中 REQ）；性能、无障碍等只有存在适用 NFR 或明确风险才进入 required。
- 适用的 `页面清单.md` 中所属阶段与 scope 有交集的每个 `PAGE-*` 恰好映射到一条 `DESIGN-*` 验收；同一实际页面沿用 PAGE ID，所属阶段可逗号列出多个阶段，只验当前有效版本并覆盖选中阶段的全部 required 行为。该行同时写入实际 MD 与 HTML 相对路径，不用通配符或根据页面显示名称猜路径。本次 `DESIGN-*` 显式引用的范围外既有页面也须核对真实 MD/HTML 与内容身份；未引用的旧页面不因此进入本次验收，scope 页面计数不变。

Bugfix：

- 覆盖 REPRO、CUR、EXP、UNCH、CON 中全部 active 条目。
- 最少包含复现、修复结果和关键不变行为回归；详见 `Bugfix测试与修复规范.md`。
- 仅验收受影响设计；无 UI 修复的设计落地章节写不适用，不生成 `DESIGN-*` 行，也不要求全套 MVP 页面产物。

页面与视觉豁免仅限 Feature 当前 scope 确无 UI 验收要求，或 Bugfix 本次修复无 UI 影响，须由真实来源与设计映射确认。此时设计落地章节写“不适用”及真实依据，不要求页面清单、MD/HTML、DESIGN 或 Token，也不生成 `DESIGN-*` 行；技术设计与全部 required 来源覆盖仍须完整。Feature scope 内已有页面保留对应 DESIGN 行，可复用有效证据，不能因本轮只改 API 就删 PAGE 或漏需求。

一条场景可以覆盖多个 Source/Design ID。覆盖完整不等于一对一生成用例。

验收、结果、追溯与页面清单表格中的单元格若含字面竖线（如管道命令、正则），使用 Markdown 的 `\|` 转义，避免改变列数；校验器会保留该单元格内容并报告格式错误行。验收 ID 使用 `SMOKE/FLOW/DESIGN/RULE-nn` 或 `BUG-REPRO/FIX/REG/RULE-nn`，数字为两至三位；数据行 ID 非法必须修正，不能忽略后继续计数。“缺失”或“missing”可以正常用于业务错误场景，只有单独的占位值才算未完成。

交付前，契约 `source_revision` 必须与上游 Metadata revision 相同；设计矩阵的 Source Revision 按来源条目的 Revision 核对（AC 未单列时继承 Parent REQ，Bugfix 未单列时继承 Metadata）。scope 内来源必须有 `covered/preserved` 的当前设计，不能用 `stale`、缺行或旧 revision 进入开发；scope 外后续阶段合法的 `planned` 保留。矩阵引用的技术方案、修复设计等文档必须真实存在，不能用非空路径代替真实产物。

## 4. 测试预算与去重

普通 MVP 的行为/风险场景通常为 8–20 条，设计落地按 MVP 页面紧凑列行。

写入时合并相同旅程、相同失败后果和相同验证方式的重复场景；按真实风险选取能证明结果的代表性情况，不穷举输入变体、状态组合或技术层。条数是参考体量，不设置每页、每层或每类的数量配额；复杂项目可超过，不得为了守数字漏掉关键约束。

## 5. 必须覆盖的验证面

### 5.1 冒烟

- 安装/依赖可用。
- 构建或静态检查成功。
- 应用能启动，关键入口可访问。
- 至少一条最核心用户旅程可走通。
- 没有阻断操作的运行时错误。

把紧密连续的启动步骤合成 1–3 条，不为每条命令各建一条。

### 5.2 功能与流程

- 从 P0/P1 AC 组合核心用户旅程。
- 同时断言适用的页面反馈、业务结果和关键数据变化，避免只断言“请求成功”。
- 一个旅程可以跨多个页面、接口和数据动作。

### 5.3 设计落地

- 当前 scope 每个页面、必要弹窗和会改变用户判断的关键状态均有行为覆盖。
- 每个 `DESIGN-*` 只对应一个 PAGE ID；通过标准从实际 HTML 提取并明确写出 `结构/组件/内容/交互/视觉/原生适配` 六类锚点，禁止只写“与原型一致”。
- 新产物使用 `output/pages/{PAGE-ID}.md` 与同名 `.html`，避免跨端同名页面覆盖；TDD 记录实际读取到的两个路径。已有产物路径沿用，不为改名重建。
- 若名称或目录不规范，先读内容：优先用 MD 页面 ID 与 HTML `meta[name="page-id"]`，缺少该元信息时可用页面标题/正文辅助。能唯一匹配同一 PAGE ID 就记录实际路径与警告后继续；零匹配、多匹配或内容冲突才失败。
- 在真实运行页面中操作，不以高保真 HTML 文件存在代替实现。
- 当前 scope 每个页面保留足以核对布局与关键视觉锚点的真实成品截图，默认方法写“真实成品截图 + 独立视觉复核”；已有 HTML 和设计说明直接作为参照。同构提示、通用组件和相同布局状态复用有效视觉证据，不按 HTML 状态与视口组合穷举截图；仅对实际布局差异、关键视觉变化或具体疑点补图。开发中已有的有效成品截图和独立复核直接复用。用户明确要求严格对照，或具体差异需要对图判断时，在对应验收行写“截图对”，按同一内容区尺寸、数据与交互状态保留原型和成品 PNG。旧契约已明确的对照要求不得自动降级。
- MD/AC 要求但 HTML 未呈现的弹窗、空/错/加载等状态，使用真实页面操作、浏览器 E2E、API 或其它行为证据验收；不生成截图对，不得由 TDD 或 Coding Agent 脑补视觉基线。
- 独立视觉验收官必须实际查看成品截图，核实对应 PAGE、当前状态及已确认的结构、组件、内容、交互入口和视觉层级；要求对照时实际查看两张图片。只看代码、DOM、测试日志或 UI 自动化结果都不算视觉验收；不得用自造渲染器的输出冒充真实原生运行效果。
- 不要求像素级机械相等；缺页、缺区域、组件/数量不符、关键内容缺失、交互入口变化、布局层级走样或原生体验违和必须失败。
- 原生平台适配只能优化窗口外壳、控件反馈和平台操作习惯，不得改变已确认的信息结构、功能和流程。先一致再优化，禁止借“超过原型”自由改版。

### 5.4 风险触发

只从真实信号触发：

| 信号 | required 验收重点 |
| :--- | :--- |
| 登录、角色、私有资源 | 未登录、水平/垂直越权、会话边界 |
| 金额、库存、额度 | 服务端重算、不可篡改、原子性/重复提交 |
| 重要或不可逆数据 | 数据完整性、失败不产生半成品、恢复/撤销约束 |
| 外部 API/服务 | 关键成功契约、失败反馈、不得重复副作用 |
| 明确 NFR | 按 NFR 的指标、阈值、采样与时间窗验证 |

没有上述信号时不生成对应测试。完整无障碍、性能/压力/容量、全浏览器兼容、mutation/property-based/fuzzing 或字段边界穷举不默认阻塞普通 MVP；有明确 NFR 或实际风险时，相关验收必须进入 required。

## 6. 验证方式

每条只选择足以证明结果的最低成本方式。同一业务断言优先在最合适的一层充分验证，其他层只验证特有失败方式与必要集成，不重跑相同边界组合；例如接口验证字段规则，浏览器验证输入、提交与错误展示。一份充分证据可支持多条验收行，不为每行另写一套测试。执行时可用证明同一结果的直接方法替换自选手段，在现有结果行记录实际动作与证据，不新增审批或报告；不得改变通过标准、适用环境或用户明确指定的验收形式：

- 纯业务规则：单元测试。
- API、数据库或外部契约：集成/API 测试。
- 用户旅程、页面联动：浏览器 E2E。
- 页面完整性与视觉：真实成品截图 + 独立视觉复核；明确对照要求按 §5.3 执行。
- HTML 未呈现的页面状态：真实页面操作、浏览器 E2E、API 或其它行为证据。
- 构建和启动：真实命令与退出码。

TDD master 不预写可执行测试代码，不猜尚不存在的函数、文件、Mock 和失败堆栈。Coding Agent 依据实际代码结构选择测试文件和命令。

## 7. `/goal` 消费与执行结果

仅在需要解释结果格式或执行证据时读取本节；契约生成使用 §1–6 和 `TDD模板.md`。

契约只定义“要证明什么”，执行期不得把状态或证据回填到契约。完整 `/goal` 在改任何代码前建立或沿用唯一运行态文件：

```text
output/tests/TDD验收结果.md
```

文件保持紧凑，先写固定元信息：

```text
- contract_sha256: sha256:<当前契约原始字节的 64 位 hex>
- run_started_at: <本轮 ISO 8601 时间>
```

再写一张表：

| TDD ID | 状态 | 实际验证动作 | 证据 |
| :--- | :--- | :--- | :--- |
| `SMOKE-01` | `pending \| pass \| fail` | `真实执行的命令或操作；复用保留原记录` | `退出码、API 结果或测试汇总` |
| `DESIGN-01` | `pending \| pass \| fail` | `独立验收官实际查看成品截图，核对该 PAGE 当前状态与设计锚点` | `actual=tests/visual/home-actual.png; reviewer=independent-visual; review=pass; blocking=0` |

执行规则：

1. 开工前提取契约全部验收 ID（`SMOKE/FLOW/DESIGN/RULE/BUG-*`），一项不漏、一项不重；无结果台账时全部为 `pending`。已有台账按本轮来源、断言、实现、依赖和环境核对影响，保留仍充分有效的证据；新增、失效或存疑项置 `pending`，不按是否为新任务清空有效结果。
2. 开发阶段按最小、可独立验证的用户闭环推进；每个闭环先运行足以证明主路径真实可用的最短冒烟。有可操作版本就立即给用户真实入口，明确已可试用、Agent 仍在测试和修正，不等全部验收通过才展示。若验证已满足某行全部断言与证据要求，可立即记录 `pass`；只证明部分行为时该行仍为 `pending`，不能用冒烟替代未覆盖的验收。
3. 涉及公共基础能力、认证权限、金额、数据迁移或不可逆操作时，按实际影响追加关联验证，不机械扩展为全量门禁。
4. 本次 Feature 或 Bugfix 范围开发完成后进入发布候选阶段，核对全部验收行；对 `pending/fail` 或证据已失效的行真实执行，并补齐必要的集成验收。已有充分证据且仍覆盖当前契约、实现、依赖和环境的行可复用，不因进入候选阶段重复执行；每项验证后立即更新动作、证据和状态。
5. 只有真实命令与退出码、API 结果或测试结果能支持功能项 `pass`。复用保留原记录或引用原结果，不冒充本轮执行；有具体变化或证据不明时核对重验，廉价检查可直接重跑，不逐行补写复用论证。代码审查、功能已实现、已失效日志、“应该通过”都不是证据。
   命令证据中的 `exit_code` 和 `failed` 表示当前断言的实际验证命令退出码与失败数，不能把被测应用的预期错误当作验证失败；例如错误输入验收可写 `exit_code=0; failed=0; expected_http=400; observed_http=400`。直接验证 CLI 非法输入并预期非零退出时，用 `expected_exit_code=1; actual_exit_code=1` 明确预期和实际；两者必须相等，不能用它掩盖测试的 `failed>0`。修复前日志保留为独立引用，不与当前 `pass` 的验证汇总混写；后一个命令成功不能抵消前一个检查失败。Bugfix 稳定复现的预期 RED 可写 `exit_code=1; failed=1; expected=RED; observed=RED`，仅适用于 `BUG-REPRO-*`。校验器会拒绝明显的未执行、推测通过和结果矛盾，但不能证明证据真实性，Agent 仍须核实证据覆盖当前断言。
6. `DESIGN-*` 必须记录 `actual` 与 `reviewer=independent-visual; review=pass; blocking=0`，实际动作如实说明已看图及核对的 PAGE 与状态，不要求包含固定措辞。图片使用 `tests/visual/` 下真实有效 PNG 的相对路径，文件名无需包含 PAGE ID；归属与内容由独立验收官实际核实。契约该行的场景、通过标准或验证方式写有“截图对”或“严格对照”时，还必须提供 `baseline`，与 actual 路径不同、尺寸相同，数据与状态一致，并实际查看原型与成品两张图片。主动提供的 baseline 也必须真实有效且与 actual 路径不同。验收行只正向写需要执行的方法，普通复核直接采用默认方法文字，避免用否定的对照表述造成歧义。UI 自动化、未实际看图或自我验收不能代替独立复核。
7. 契约变化时先核对 ID、断言与来源的实际影响，只使受影响结果失效，再更新台账中的契约哈希；不得仅改哈希而跳过影响核对。实现、依赖或环境变化同样只使受影响 `pass` 失效，按需重验、重截、重审，保留无关且仍有效的结果。
8. 完成前用脚本或命令机械核对：契约哈希一致、契约 ID 集合与结果 ID 集合完全相等且无重复、`pending=0`、`fail=0`、`pass=总数`，每个 `pass` 的动作和证据有效。

能定位已安装的 tdd-master 时，完成前用同一校验器的结果模式复核：

```text
<PYTHON3> "<SKILL_ROOT>/validators/check_delivery_contract.py" --result "{项目名}/output"
```

无法定位校验器时才使用等价脚本机械比对，严禁靠人工目测计数后宣布全绿。

**无真实有效证据便凭推测倒填、把阻塞项写成 `pass`，不得宣称验收通过。用户叫停立即停止；外部条件无法取得时停止受阻尝试，保留未验证项并说明实际停点，不为清空 `pending` 反复取证。可操作版本可以先交用户试用，复用证据不减少任何 required 验收项。**
